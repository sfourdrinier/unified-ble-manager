# Connection-scoped ordered notification ingress

## Goal and meaning

Provide an ordered, loss-reporting collection of notifications across selected characteristic instances on every supported UBM backend. This is the order in which a defined connection-owned host ingress accepts events; it is not a claim about radio transmission order, values the operating system never delivered, or completeness of a device's history. Do not synthesize or infer ordering from timestamps or independently scheduled characteristic streams.

## Consumer contract

A collection is opened on one current connection/database generation with a nonempty, immutable set of distinct characteristic instances and their requested delivery modes. It exposes one bounded ordered stream and an explicit asynchronous close. A value carries the collection and connection generation, member identity, owned bytes, delivery kind, and a strictly increasing, losslessly transported ingress ordinal. The ordinal is assigned once before per-characteristic fan-out or staging and is not regenerated in JavaScript. Existing individual subscriptions continue to work and must retain their own ownership of physical notification registrations.

The collection reports loss, source failure, database change, disconnect, explicit closure, and cleanup outcomes without representing an uncertain tail as complete. A per-characteristic consumer cannot infer loss from gaps in global ordinals, because other members may account for those ordinals. A bounded queue reserves a terminal path: if it cannot preserve accepted values and control events, it terminates with explicit loss rather than silently dropping a marker. When the native source cannot attribute a loss to one member, the collection reports an unknown affected count or scope rather than inventing precision.

Install the group route and its bounded staging before the first CCCD enable. Sequential setup buffers ingress events until all members are acquired. A failed or aborted setup returns structured failure including partial acquisition and cleanup status; it never disables a physical subscription owned by another consumer. Teardown and service change fence the exact generation, account for already accepted events and uncertain tails, and cannot deliver old-generation callbacks into a new collection. Reconnect requires a new collection. Retain all accepted raw values and diagnostics; an ordered collection alone never authorizes an application-level history acknowledgement.

## Boundaries and work

- **Android:** `OwnedAndroidGattRadio.kt` must serialize callback admission, subscription staging and activation under a connection-generation owner before any per-characteristic staging. The current split `isActive`/`stage` check can lose an activation-racing callback, and staging overflow is not conveyed by its list-only activation result. Route ordinals, values and loss through `OwnedRadioPort.kt`, the mobile host/wire, and the React Native provider.
- **Apple mobile:** establish the same owner at CoreBluetooth delegate ingress in `ios/Owned/OwnedCoreBluetoothProtocolRadio.swift` and its cancellation/notification classification path, preserving the callback decision through the Swift adapter and mobile host/wire.
- **Desktop:** replace separately scheduled per-characteristic forwarding with a single connection-owned receive/demultiplex path in `crates/ubm-desktop/src/btleplug_backend.rs`, before `central.rs` routes to per-instance hubs. Preserve full instance/epoch identity, source loss and closure. On BlueZ, define the ingress at the serialized merged native source unless the upstream merge is changed and qualified; on WinRT serialize concurrent callbacks at the publishing boundary. CoreBluetooth, WinRT and BlueZ must each be implemented and tested.
- **Web:** serialize accepted DOM notifications at a connection-owned ingress before characteristic stream fan-out. The resulting order is callback-ingress order, not peripheral transmission order.
- **Boundaries and consumers:** add a group operation and ordered event types to the public and backend GATT contracts, version the mobile and desktop transport contracts as required, and carry values and terminal controls through Node N-API, Electron IPC and Tauri without recreating ordinals. Keep existing subscribers compatible. Update Expo and Bun WHOOP consumers to select the ordered collection for multi-characteristic capture.
- **Recording:** the current per-route pump/journal append order is not original ingress order. Durable ordered capture must admit the same group FIFO and retain ordinals, loss controls and generation across restart. Do not describe the existing journal as ordered acquisition.

## Verification and status

Implementation has not started. For every backend and actual public transport, use deterministic interleaved A/B callbacks, callbacks during CCCD setup, independent existing subscribers, partial enable/abort, bounded overflow, unattributable source loss, disconnect/service change/reconnect, duplicate UUID instances, stale callbacks and transport closure. Android additionally needs a deterministic activation-versus-callback regression and staging-overflow regression. Check loss controls and clean ownership on every exit, and test durable replay and crash/ack boundaries when durable group capture is implemented. Native synthetic tests, native builds, and physical-radio experiments are distinct evidence levels. Device-specific complete-history and ACK behavior require separate protocol evidence and physical testing.

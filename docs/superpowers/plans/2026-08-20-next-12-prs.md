# 1. Executive recommendation

`4.0.0-rc.1` should be treated as the **last public prototype**, not as a compatibility baseline. There is no good reason to carry provisional names, duplicated host façades, manually synchronized identity fields, or low-level protocol types into stable 4.0 merely because they already exist in RC1.

The right strategy is:

1. Use PRs 1–4 as an explicit **pre-stable contract-reset window**.
2. Remove accidental public complexity rather than deprecating it.
3. Publish `4.0.0-rc.2` only after the portable application API, host factories, capabilities, errors, GATT object model, lifecycle conventions, and canonical scan semantics are coherent.
4. Make PRs 5–11 additive against that frozen portable contract, with only the explicitly staged Expo-config and Tauri-install/CLI cleanups allowed at RC4/RC5.
5. Use PR 12 for live qualification, performance gates, final evidence, and stable publication.

This is not a rewrite of the reliable core. The existing ownership, generations, bounded streams, cancellation, TCK, protocol negotiation, diagnostics, and evidence model are unusually strong. The work is to preserve those guarantees **inside** the library while presenting a much simpler consumer surface.

The stable product should be defensible as:

> The most complete, lifecycle-safe, evidence-driven BLE central stack for TypeScript across React Native, Expo, Web Bluetooth, Node, Electron, and Tauri.

That claim is credible only if the package combines:

- a five-minute success path;
- complete modern BLE-central functionality;
- honest platform differences;
- deterministic cleanup and recovery;
- best-of-breed Expo and Tauri integration;
- strong testing and diagnostics;
- measured performance;
- support labels backed by exact evidence rather than compilation alone.

# 2. Immediate consequence of having zero external consumers

## 2.1 Breaking-change policy before stable

The package should make breaking RC1 changes where they improve the stable contract. Do **not** add deprecation aliases, overloads that preserve awkward shapes, duplicate legacy entrypoints, or automatic translation layers for an API no one relies on.

Permitted for the **portable runtime/application contract** through PR4:

- rename public classes, methods, options, and event fields;
- remove public generic parameters that expose backend identity internals;
- move low-level types to `/advanced` or `/backend-sdk`;
- replace mandatory branded deadlines with optional `timeoutMs` in the application layer;
- replace mandatory stream capacities with documented presets and optional expert overrides;
- replace manually passed `clientId`, `managerId`, and `hostSessionScope` with host-derived identity, while keeping restoration-bound identity deterministic across relaunch;
- replace manual GATT path arguments with generation-bound object handles;
- unify local and IPC manager types;
- bump the internal IPC/native protocol and remove the old protocol instead of negotiating both indefinitely;
- remove aliases such as public `IpcBleManager` versus `TauriBleManager` when one common manager contract is sufficient;
- replace RC1's narrow `ScanFilter` dialect with the canonical `ScanQuery` v1 shape, Boolean semantics, normalization, and matcher before the RC2 freeze.

Two explicitly provisional host/tool surfaces have later freeze points:

- the Expo config-plugin schema and RC1 five-field restoration configuration may break through PR10 and freeze at `4.0.0-rc.4`;
- Tauri Cargo installation/version coordination and CLI command taxonomy may break through PR11 and freeze at `4.0.0-rc.5`.

Those exceptions may improve host configuration and distribution only. They may not redesign the portable `BleManager`, GATT, error, capability, cleanup, or scan-query semantics frozen at RC2.

Not permitted in the portable runtime contract after PR4 without a release-blocking correctness reason:

- renaming public application methods;
- changing normal return shapes;
- changing error-code meaning;
- changing scan-query semantics;
- changing persistence formats without a versioned decoder;
- adding a second competing way to perform the same normal workflow.

## 2.2 No compatibility tax for hypothetical users

The **library** still publishes an RC1→RC2 table at `4.0.0-rc.2` so implementers can see the freeze. **First-party product clients do not migrate there.** They stay on `4.0.0-rc.1` until stable `4.0.0` and follow the one-pass recipe in section 10.

For anyone who does move at an RC, the policy is:

- old API removed;
- exact replacement documented;
- no runtime warning period;
- no compatibility package;
- no hidden environment switch;
- no permanent `legacy` namespace.

## 2.3 Portable runtime API and semantics freeze checkpoint

`4.0.0-rc.2`, produced after PR4, is the portable runtime application-API and application-semantics freeze candidate. It must pass a committed public API report for every public subpath and a committed semantic contract suite for behavior that TypeScript reports cannot capture.

The RC2 freeze explicitly includes:

- host factories and application-visible identity rules;
- manager, peer, connection, GATT, subscription, cleanup, error, and capability vocabulary;
- `OperationOptions`, stream presets, and lifecycle conventions;
- the core public `ScanQuery` v1 algebra and predicate semantics; later optional predicate fields (the first planned addition is `ScanClause.peers` in PR5) may be added only additively under those rules;
- exact scan Boolean semantics;
- UUID/byte-pattern/query normalization rules;
- the canonical pure residual matcher and semantic-digest rules;
- the distinction between continuous scan, system chooser, and peer-directory retrieval.

PR9 is therefore **not** allowed to replace or reinterpret scan filtering. It may:

- compile the already-frozen query into native and residual projections;
- improve native pushdown and platform scan controls;
- expose additive plan diagnostics;
- add an optional derived lost-peer timeout on the existing coalesced current-view;
- improve performance without changing canonical match outcomes.

For every normalized query and normalized observation, PR9's optimized path must be observationally equivalent to PR4's pure canonical matcher. A backend planner that cannot prove a safe pushdown must use a broader native scan and residual filtering rather than changing semantics.

PRs 5–12 may add capabilities and methods only when they fit the frozen vocabulary. They must not redesign it.

## 2.4 Host integration and tooling freeze checkpoints

The release uses staged freezes rather than pretending every provisional host surface is complete at RC2:

| Surface | Last planned breaking milestone | Freeze checkpoint |
|---|---:|---|
| Portable runtime manager/GATT/error/capability/scan semantics | PR4 | `4.0.0-rc.2` |
| Expo config-plugin schema and restoration configuration | PR10 | `4.0.0-rc.4` |
| Tauri Cargo/npm coordination, installation shape, and public CLI taxonomy | PR11 | `4.0.0-rc.5` |

Rules:

- later host/tool changes cannot alter the RC2 portable runtime semantics;
- each staged freeze receives its own API/schema snapshots and migration table;
- the stable `4.0.0` release contains no known planned breaking change in any surface;
- a release-blocking correctness/security defect may still force a pre-stable correction, but it must be explicitly documented and re-qualified.

## 2.5 First-party client freeze during this train

The one in-development consumer will not take intermediate RCs.

- Pin `unified-ble-manager@4.0.0-rc.1` (and the matching Tauri path plugin) until `4.0.0` is on npm `latest`.
- Do not chase PR heads, canaries, `rc.2`, `rc.3`, `rc.4`, or `rc.5` in product apps.
- Keep BLE behind one adapter module (the existing `BLEService` / host equivalent). That module is what you rewrite once.
- When `4.0.0` is published, migrate in one pass using section 10. Expo plugin v2 and the Tauri crates.io install are part of that same pass, not later follow-ups.

This avoids rewriting construction at RC2, scan again at PR9, Expo config at RC4, and Cargo at RC5.

# 3. Audited RC1 baseline

## 3.1 What is already excellent and must survive

At the audited commit, the repository already has:

- a host-neutral manager and explicit backend attachment;
- generation-bound attachment, connection, database, service, characteristic, descriptor, and subscription identities;
- explicit owner and borrower semantics;
- asynchronous cleanup records;
- bounded streams with item, byte, reserved-control, and overflow policy limits;
- `AbortSignal`, monotonic deadlines, cancellation acknowledgement, and exact operation settlement;
- advertisement provenance and absent/unavailable field modeling;
- GATT descriptor I/O;
- maximum-write-length observations and long-write partial-commit receipts;
- deterministic virtual-time backends and fault injection;
- a substantial TCK covering identity, scan arbitration, connection ownership, GATT, subscriptions, restoration, lifecycle, diagnostics, Web, and IPC;
- React Native Android and Apple protocol implementations;
- Web Bluetooth integration;
- BlueZ, CoreBluetooth, and WinRT desktop backends;
- Electron main/renderer ownership and IPC;
- a working Tauri v2 Rust plugin and authenticated webview protocol;
- CLI diagnostics and TCK execution;
- packed-consumer checks, native prebuild delivery, SBOM, license inventory, provenance, and evidence infrastructure.

These are not implementation details to throw away. They are the reliability substrate that should power the simpler stable API.

## 3.2 Concrete RC1 issues to correct before stable

### A. The root entrypoint exposes backend-authoring complexity

`src/index.ts` exports application helpers alongside:

- `attachBleBackend` and provider construction;
- ownership authorities;
- portable attachment/path types;
- branded `Capacity`, `Deadline`, IDs, and generations;
- backend contract types and raw stream records.

That is useful for backend authors, but it makes the normal package surface look like a protocol SDK. Stable 4.0 needs a small application root and explicit expert entrypoints.

### B. Public application types leak backend generics

The current manager family carries generic parameters such as attachment and backend identity through normal application types. Those generics enforce useful internal correctness, but consumers should not need to understand or name them. The application API should be non-generic; the backend SDK can remain generic.

### C. The normal operation API is too low-level

Current public operation options require explicit nullable `signal` and branded monotonic `deadline` fields. Scan and subscription options require callers to construct stream capacities. These are excellent internal contracts and poor five-minute defaults.

The stable application layer should accept:

```ts
interface OperationOptions {
  signal?: AbortSignal
  timeoutMs?: number
}
```

The library should normalize that once to the existing deadline/cancellation machinery. Advanced callers can still provide exact deadlines and stream budgets through `/advanced`.

### D. Host factories require identity bookkeeping that the host already knows

React Native currently asks for `clientId`, `managerId`, and `hostSessionScope`; Node and Web also ask for IDs; the Expo restoration object duplicates five related strings. Requiring applications to keep them synchronized creates avoidable restoration and ownership bugs. The replacement must distinguish two identity classes: ephemeral runtime identity may be securely generated per manager/attachment, while restoration-bound identity must remain stable across process relaunch and app updates. The trusted native host should deterministically derive restoration client/session identity from the application identifier plus the one configured restoration ID and optional generation; it must not use per-launch randomness, wall-clock time, or the package patch version.

### E. Tauri still exposes transport injection as the normal path

The Tauri factory currently requires callers to pass `invoke` and `Channel`. That is valuable for tests and custom environments, but the standard Tauri entrypoint should import the official API and require no transport plumbing:

```ts
const ble = await createTauriBleManager()
```

Keep `createTauriBleManagerWithEnvironment(...)` for test injection and unusual hosts.

### F. Local and IPC resources are not semantically identical yet

The current IPC manager contains temporary projections that must not survive stable 4.0:

- connection generation is hardcoded to `'1'`;
- Tauri attachment/adapter/database identity is fabricated in the renderer;
- the lifecycle stream exists but is not wired as the local connection stream is;
- characteristic `indicate` is folded into `notify`;
- subscription values lose the notification-versus-indication field;
- write completion fabricates a confirmed success receipt;
- database generation is hardcoded;
- some malformed IPC data throws `TypeError` rather than the same normalized BLE error used locally.

The trusted host must issue all resource identity and terminal receipts. A renderer must never invent them.

### G. The built-in capability catalog is too small for the implemented product

The capability infrastructure is sophisticated, but the built-in catalog currently centers on maximum write length and long write. Stable 4.0 needs typed capabilities for discovery models, known peers, pairing, reconnect intents, security, service changes, link controls, background behavior, and host-specific limits.

### H. Errors are normalized but not yet actionable enough

The current retry disposition is mostly `never` versus `caller-decides`. A best-in-class library should tell the application whether recovery requires:

- a safe retry;
- backoff;
- a permission request;
- opening settings;
- waiting for Bluetooth power;
- reconnecting;
- rediscovering GATT;
- repairing;
- reducing payload size;
- recreating a manager after backend reset;
- explicit user action.

The library must supply guidance without silently taking product-level action.

### I. GATT is internally precise but externally path-oriented

The current portable path model is strong. The five-minute API should not require callers to pass full path records back into database methods. Stable 4.0 should expose service, characteristic, and descriptor objects that retain those paths internally and invalidate correctly on generation changes. These objects are not a return to the 3.x-style immortal mutable device graph: they are lease-scoped, database-generation-bound views, they never silently reconnect or rediscover, and every operation validates the complete hidden path before dispatch.

### J. Expo configuration works, but it is not yet a complete Expo product

The plugin correctly reconciles permissions and supports central background mode and restoration identity. It still lacks:

- a one-identifier restoration model;
- runtime permission helpers;
- StrictMode-safe provider/hooks;
- a development-build-first quickstart;
- an explicit Expo Go failure message;
- optional Android connected-device foreground-service ownership;
- a real packed-package example with reconnect/restoration flows;
- a devtools surface for adapter, resource, and trace inspection.

### K. Tauri distribution is functional but non-standard

The Rust crate is currently consumed by a path inside `node_modules`. That works for the first-party app but is not the best third-party Tauri experience. Tauri’s normal plugin model is a published Cargo crate plus a JavaScript API package, permission files, and capability configuration. The Rust crate and npm package should remain version-locked and independently verifiable.

# 5. Design doctrine for all 12 PRs

## 5.1 Preserve the reliability moat

1. **No silent backend fallback.** A failed backend never substitutes Web Bluetooth, Noble, a mock, or another radio stack.
2. **Bytes stay bytes.** BLE payloads remain `Uint8Array`; Base64 exists only in explicit codecs.
3. **Cancellation remains first-class.** Blocking operations accept `AbortSignal`; timeouts normalize to monotonic deadlines.
4. **Streams remain bounded.** Defaults are presets, not unbounded queues.
5. **Handles remain generation-bound.** Reconnect, service change, host reload, and backend reset invalidate stale resources.
6. **Cleanup remains observable.** Stop, unsubscribe, release, and destroy retain cleanup evidence.
7. **Capabilities are runtime truth.** Platform-name checks do not grant support.
8. **The trusted host owns the radio.** Webviews/renderers never load or forge native state.
9. **No imported global singleton.** Applications explicitly create and destroy managers.
10. **No hidden product policy.** Retry/reconnect/background behavior is opt-in and caller-configured.
11. **Deterministic proof is not live proof.** Support labels remain evidence-derived.
12. **No duplicate authority.** Each concept has one schema, one matcher, one error catalog, or one lifecycle implementation.

## 5.2 Three intentional API layers

### Application layer — package root and host entrypoints

For nearly every app developer:

- non-generic manager/peer/connection/GATT types;
- optional `signal` and `timeoutMs`;
- stream presets;
- object handles;
- normalized `BleError`;
- high-level scopes and helpers;
- typed capabilities.

### Advanced layer — `unified-ble-manager/advanced`

For unusually demanding consumers:

- explicit monotonic deadlines;
- stream budgets and overflow policies;
- raw cleanup records;
- portable paths and snapshots;
- ownership/join/transfer controls;
- trace settings;
- exact write receipts and operation correlations.

This layer should wrap the same implementation, not fork behavior.

### Backend-author layer — `unified-ble-manager/backend-sdk`

For first- and third-party backend authors:

- generic branded identities;
- backend provider contracts;
- capability registration/evidence binding;
- protocol/TCK authoring;
- deterministic fixtures;
- adapter selection and host attachment.

## 5.3 DRY authorities

| Concept | Authority |
|---|---|
| Public application API | committed API-extractor reports and type fixtures |
| Backend identity/path semantics | backend contract |
| Native and desktop wire values | one versioned generated schema family |
| Characteristic/service/descriptor properties | one canonical GATT model |
| Capability IDs, limits, and TCK bindings | one built-in capability catalog |
| Error recovery | one normalized recovery-action catalog |
| Scan semantics | PR4/RC2 query algebra, golden vectors, normalization, semantic digest, and one canonical residual matcher |
| Peer persistence | one versioned opaque `PeerReference` format |
| Reconnect policy | one deterministic supervisor over public primitives |
| Expo configuration | one strict schema shared by validation, mods, docs, and tests |
| Platform support | generated evidence projection |
| Examples | executable source imported into documentation |
| Release truth | immutable package/crate artifacts, checksums, SBOM, provenance, and evidence |

## 5.4 TDD order for every feature PR

1. Public type tests and negative compile fixtures.
2. Contract/TCK scenario and controller actions.
3. Deterministic backend implementation.
4. Shared core/manager implementation.
5. First-party backend implementations or explicit unsupported/limited registrations.
6. Generated native/IPC projection.
7. Host composition and packed-consumer tests.
8. Executable examples and generated docs.
9. Physical scenario and evidence record when a live support claim changes.

Do not start with one native backend and reverse-engineer a portable contract afterward.

## 6.2 One non-generic application manager

```ts
interface BleManager {
  readonly adapter: BleAdapter
  readonly capabilities: BleCapabilities
  readonly diagnostics: BleDiagnostics

  scan(options?: ScanOptions): Promise<ScanSession>
  choose(options: ChoosePeerOptions): Promise<BlePeer>
  find(options: FindPeerOptions): Promise<BlePeer>

  knownPeers(options?: KnownPeerOptions): Promise<readonly BlePeer[]>
  resolvePeer(reference: PeerReference, options?: OperationOptions): Promise<BlePeer | null>

  connect(peer: BlePeer | PeerReference, options?: ConnectOptions): Promise<BleConnection>
  withConnection<T>(
    peer: BlePeer | PeerReference,
    options: ConnectOptions,
    use: (connection: BleConnection) => Promise<T>
  ): Promise<T>

  destroy(): Promise<CleanupRecord>
}
```

Unsupported discovery modes reject with typed capability errors. They do not silently switch semantics. A Web app uses `choose`; a continuously scanning host uses `scan`/`find`. Cross-host apps branch on `manager.capabilities` or `manager.discovery.kind`. Returning the same public `BleManager` façade from local, Electron, and Tauri factories means vocabulary parity—not capability parity: capability documents are issued by the trusted host, platform limitations remain visible, and a renderer/webview cannot select the radio backend, claim support, or fabricate resource identity.

## 6.3 Application operation options

```ts
interface OperationOptions {
  readonly signal?: AbortSignal
  readonly timeoutMs?: number
}
```

Defaults are operation-specific and documented. The advanced layer exposes exact deadlines when needed.

## 6.4 Canonical scan query v1

The scan dialect is part of the RC2 freeze, not deferred to PR9:

```ts
interface ScanQuery {
  /** Omitted means match every observation the host is permitted to expose. */
  readonly anyOf?: readonly ScanClause[]
  /** Matching any exclusion removes the observation after positive matching. */
  readonly exclude?: readonly ScanClause[]
}

interface ScanClause {
  readonly services?: {
    readonly any?: readonly UuidInput[]
    readonly all?: readonly UuidInput[]
  }
  readonly names?: {
    readonly exact?: readonly string[]
    readonly prefixes?: readonly string[]
  }
  readonly manufacturerData?: {
    readonly any?: readonly ManufacturerDataPattern[]
    readonly all?: readonly ManufacturerDataPattern[]
  }
  readonly serviceData?: {
    readonly any?: readonly ServiceDataPattern[]
    readonly all?: readonly ServiceDataPattern[]
  }
  readonly rssi?: { readonly minimum?: number; readonly maximum?: number }
  readonly connectable?: boolean
}
```

`ScanClause.peers` is **not** part of RC2. PR5 adds it additively. PR4 rejects unknown clause keys rather than ignoring them.

Frozen semantics:

- `anyOf` clauses are ORed;
- fields inside one clause are ANDed;
- values in each `*.any` list are ORed within that field; when PR5 adds `peers`, that list is ORed the same way;
- `names.exact` and `names.prefixes` form one OR set: either an exact-name or prefix match satisfies the names field;
- each `*.all` list requires every listed pattern;
- when both `any` and `all` are supplied for one field, both constraints must hold;
- exclusions are ORed and applied after positive matching;
- an omitted `anyOf` means match-all, while an explicitly empty array is invalid;
- missing/unavailable observation fields do not satisfy predicates that require them;
- masks require equal-length prefixes and use exact byte-mask semantics;
- one pure canonical matcher defines observable behavior on every host.

PR9 may optimize execution, but it may not change this contract.

## 6.5 Peers and persistent references

```ts
interface BlePeer {
  readonly id: string                    // opaque, backend-scoped
  readonly reference: PeerReference | null
  readonly name: string | null
  readonly sources: readonly PeerSource[]
  readonly lastAdvertisement: Advertisement | null
}

interface PeerReference {
  readonly version: 1
  readonly backendId: string
  readonly scope: 'application' | 'origin' | 'system'
  readonly opaqueId: string
}
```

A reference is persistable and resolvable by the same backend scope. It does not claim a globally stable physical identity.

## 6.6 Object-oriented GATT without losing path safety

```ts
await ble.withConnection(peer, { timeoutMs: 10_000 }, async connection => {
  const gatt = await connection.discover({ timeoutMs: 10_000 })
  const heartRate = gatt.service('180d')
  const measurement = heartRate.characteristic('2a37')

  const subscription = await measurement.subscribe({ overflow: 'latest' })
  try {
    for await (const event of subscription.values) {
      console.log(event.value, event.delivery) // notification | indication
    }
  } finally {
    await subscription.unsubscribe()
  }
})
```

The service/characteristic objects retain complete generation-bound paths internally. Duplicate UUID occurrences require an explicit occurrence selector; ambiguity never selects an arbitrary item. They are immutable views owned by one connection/database generation—not 3.x-style global `Device` objects. They do not survive reconnect, do not auto-refresh after Service Changed, do not carry hidden reconnect policy, and do not cache a mutable `lastValue` as authoritative state.

## 6.7 Typed capabilities

```ts
if (ble.capabilities.supports(BLE_FEATURES.security.pair)) {
  await ble.security.pair(peer)
}

const feature = ble.capabilities.get(BLE_FEATURES.connection.phy)
console.log(feature.state, feature.limits, feature.limitations)
```

The open namespaced registry remains, but built-ins are generated from one typed catalog.

## 6.8 Actionable errors

```ts
try {
  await connection.discover({ timeoutMs: 10_000 })
} catch (error) {
  if (error instanceof BleError) {
    for (const action of error.recovery.actions) {
      // request-permission, wait-for-adapter, reconnect, rediscover-gatt, etc.
    }
  }
}
```

Recovery metadata guides the caller. It never silently retries, opens settings, pairs, or recreates a manager.

## 6.9 Explicit reconnect supervision

```ts
const supervisor = createConnectionSupervisor(ble, peer, {
  connection: { intent: 'when-available' },
  retry: {
    initialDelayMs: 500,
    maximumDelayMs: 30_000,
    multiplier: 1.8,
    jitter: 0.2
  },
  configure: async connection => {
    const gatt = await connection.discover()
    return gatt.service('180d').characteristic('2a37').subscribe()
  }
})

supervisor.start()
```

The supervisor is caller-owned and deterministic. The core does not reconnect merely because a connection was once made.

# PR 1 — Pre-stable public contract reset

## Suggested PR title

`feat!: reset the pre-stable public API and host factories`

## Branch

`feat/4.0-public-contract-reset`

## Purpose

Create the public contract that stable 4.0 should actually support for years. This PR deliberately breaks RC1 and removes accidental exposure of internal protocol mechanics. It does **not** weaken the core; it places a focused application façade over it and moves expert contracts to explicit entrypoints.

## Why this must be first

Every later feature—known peers, reconnect, pairing, link controls, scan planning, and Expo hooks—will compound whichever vocabulary exists. Adding those features before correcting the root API would either:

- force consumers to carry backend generics and path records forever;
- require compatibility aliases immediately after stable;
- create separate local, IPC, React, and Expo APIs;
- make the eventual cleanup a true SemVer break.

There are no external consumers, so this is the correct moment to fix it.

## Public decisions to lock in this PR

### 1. Root package becomes application-only

The root should export only concepts normal application code needs:

- `BleManager`;
- `BleAdapter` and adapter state;
- `BlePeer`, `PeerReference`, advertisements;
- `ScanSession` and discovery types;
- `BleConnection` and lifecycle events;
- `GattDatabase`, `GattService`, `GattCharacteristic`, `GattDescriptor`;
- `GattSubscription` and values;
- `BleCapabilities` and built-in feature constants;
- `BleError` and cleanup types;
- public operation options;
- high-level helpers and codecs that do not load a host.

Remove from the root and move to `/advanced` or `/backend-sdk`:

- `attachBleBackend`;
- `createBleManagerFromProvider`;
- provider/backend construction types;
- ownership authorities and transfer grants;
- generic attachment/identity types;
- portable raw paths;
- branded `Capacity`, `Deadline`, `AttachmentId`, `ManagerId`, and operation correlations;
- raw `BoundedAsyncStream` control records;
- feature implementation registrations and TCK authoring details;
- backend contract errors intended for implementers.

The root may re-export simple read-only capability descriptors and cleanup records, but not implementation registrations.

### 2. Public application classes are non-generic

Stable application declarations should not contain parameters such as:

```ts
BleManager<Attachment, Identity>
Connection<Attachment, ConnectionScope>
GattDatabase<Attachment, Connection, Database>
```

Those remain valid inside `/backend-sdk`. Public app types should be structurally stable and opaque:

```ts
interface BleManager { ... }
interface BleConnection { ... }
interface GattCharacteristic { ... }
```

The implementation can wrap generic core resources in internal adapters without losing static safety.

### 3. One public name per resource

Use these names consistently across all hosts:

| Concept | Stable name |
|---|---|
| Application manager | `BleManager` |
| Remote BLE entity | `BlePeer` |
| Persistable opaque locator | `PeerReference` |
| Active link lease | `BleConnection` |
| Discovered GATT database | `GattDatabase` |
| GATT service | `GattService` |
| GATT characteristic | `GattCharacteristic` |
| GATT descriptor | `GattDescriptor` |
| Active characteristic delivery | `GattSubscription` |
| Normalized public error | `BleError` |

Do not expose public `IpcConnection`, `TauriConnection`, `LocalConnection`, or `ReactNativeConnection` variants. Host-specific classes may exist internally.

### 4. Simple operation options

Add one public options base:

```ts
export interface OperationOptions {
  readonly signal?: AbortSignal
  readonly timeoutMs?: number
}
```

Rules:

- omitted timeout means the operation-specific documented default;
- `timeoutMs: Infinity` is rejected; explicit “no timeout” is `timeoutMs: null` only if the team decides indefinite operations are safe for that method;
- zero, negative, NaN, and non-finite values reject synchronously with `argument.invalid`;
- the application layer converts `timeoutMs` to a monotonic internal deadline exactly once;
- advanced APIs can accept exact `Deadline` values;
- nested wrappers must never reset an existing deadline and accidentally extend the operation.

### 5. Stream presets replace mandatory capacity construction

Normal scan/subscription options should accept:

```ts
type StreamPreset = 'latest' | 'balanced' | 'lossless-bounded' | 'custom'
```

Recommended default meanings:

| Preset | Intended use | Overflow |
|---|---|---|
| `latest` | UI/status values where the newest value matters | replace/drop oldest |
| `balanced` | normal scan and sensor notifications | bounded drop-oldest with visible notice |
| `lossless-bounded` | command/response protocols that must fail rather than drop | terminal overflow error |
| `custom` | advanced budgets supplied explicitly | caller selected |

Exact limits remain available through `/advanced`. The public stream still exposes overflow and terminal notices; “preset” does not mean hidden data loss.

### 6. Factories derive identity internally—with separate ephemeral and restoration rules

Normal factory options should contain only product-relevant choices:

```ts
interface BleManagerCreateOptions {
  readonly instanceId?: string
  readonly adapterId?: string
  readonly diagnostics?: DiagnosticsOptions
}
```

Identity taxonomy:

1. **Ephemeral runtime identity** — manager IDs, operation correlations, leases, attachment nonces, and backend generations may be cryptographically random or host-monotonic. They exist for one runtime attachment and are never restoration keys.
2. **Stable restoration identity** — any client/session identity used to adopt a native restoration journal must be deterministic across relaunch. The trusted native host derives it from a versioned domain separator, the trusted application identifier (for example the iOS bundle identifier), the single application-facing restoration ID, and the optional app-controlled restoration generation.
3. **Persisted peer references** — arrive later in PR5 and use their own versioned backend-scoped format. They are not manager IDs and do not reuse restoration tokens.

Rules:

- `instanceId` is optional and exists only for apps intentionally creating multiple independent runtime managers;
- `instanceId` must not silently alter restoration identity; apps needing multiple restoration domains configure distinct restoration IDs;
- `clientId`, `managerId`, owner IDs, attachment IDs, generations, and host-session scopes are library/host concerns;
- per-launch random values, wall-clock timestamps, package patch versions, build numbers, and OS versions must never participate in restoration identity;
- changing the application identifier, restoration ID, or explicit restoration generation intentionally produces a different restoration domain;
- ordinary package/app updates preserve the restoration domain;
- the native host returns the derived opaque restoration identity during bootstrap; JavaScript does not reconstruct or forge it;
- tests inject deterministic ephemeral generators and fixed trusted app configuration through `WithEnvironment` factories.

### 7. Host factories are zero-plumbing

Target signatures:

```ts
createReactNativeBleManager(options?: BleManagerCreateOptions): Promise<BleManager>
createExpoBleManager(options?: BleManagerCreateOptions): Promise<BleManager>
createWebBleManager(options?: BleManagerCreateOptions): Promise<BleManager>
createTauriBleManager(options?: BleManagerCreateOptions): Promise<BleManager>
```

Host-only extras (`adapterId` on Node, chooser filters on Web, and so on) are optional fields on this one bag or a nested `host` object. Do not invent parallel types such as `ExpoBleManagerCreateOptions`. Expo configuration comes from the plugin/native host, not from a second factory options interface.

Tauri should import `invoke` and `Channel` from `@tauri-apps/api/core` in the Tauri-only entrypoint. Add `@tauri-apps/api` as an optional peer dependency. The testable transport constructor moves to:

```ts
createTauriBleManagerWithEnvironment(environment, options?)
```

Web should return one manager, not `{ chooser, manager }`. The chooser becomes a discovery capability on the manager.

React Native should not ask app code to import the generated TurboModule or provide a clock.

### 8. No compatibility aliases

Delete RC1 aliases rather than retaining both:

- no `TauriBleManager` alias for a public `IpcBleManager`;
- no root export of the old generic manager;
- no deprecated factory overload accepting three identity strings;
- no old Web tuple return shape;
- no duplicate `Portable*` types in the application root.

The migration guide is the compatibility mechanism.

# PR 2 — Canonical cross-host semantics, capabilities, and recovery

## Suggested PR title

`feat!: unify cross-host semantics, capabilities, and recoverable errors`

## Branch

`feat/4.0-cross-host-semantics-v2`

## Purpose

Make local/native, Electron renderer, Tauri webview, and browser resources carry the same truthful identity, lifecycle, capability, error, stream, and terminal data. At the same time, establish the capability and recovery vocabulary every later feature will use.

This PR removes all temporary renderer-side identity and receipt fabrication.

## Why these topics belong together

Capabilities, errors, lifecycle events, and receipts are the serialized semantic boundary between trusted hosts and application façades. The **numbered PR2 contract** still ships them together so hosts do not grow a second DTO family. Execution, however, is pre-authorized as stacked lettered PRs: **PR2A** lands generated protocol/DTO v2, host-issued identity, lifecycle streams, notification shape, and truthful receipts; **PR2B** lands the capability catalog, recovery actions, public `BleError`, v1 deletion, and all-host TCK/ABI proof. Mixing the wire bump with a new error vocabulary in one merge hides semantic bugs. Partial public surfaces stay unexported until numbered PR2 is complete. No RC is published between 2A and 2B.

## Contract decisions

### 1. Bump to a single v2 host protocol and remove v1

The package has no deployed protocol peers. Create one versioned schema family for:

- attachment/adapter identity;
- peer and peer-reference records;
- connection identity/generation/lifecycle;
- database generation;
- GATT topology records;
- characteristic properties;
- notification values;
- operation terminal records and write receipts;
- cleanup records;
- capability descriptors and limits;
- normalized errors and recovery actions;
- bounded stream value/overflow/terminal items.

Generate or validate projections for:

- TypeScript;
- Rust/Tauri;
- Electron IPC;
- React Native protocol bindings where shapes overlap;
- deterministic fixtures.

Change `unified-ble-manager:v1` and any protocol-v1-only symbols to v2, then remove v1 implementation and negotiation. Keep internal protocol versioning for future safety, but do not maintain unused dual stacks.

### 2. Trusted host issues every identity

The application/renderer receives immutable host-issued records. It never constructs:

- attachment IDs;
- backend instance/generation;
- adapter generation;
- connection ID/generation;
- owner lease IDs;
- database ID/generation;
- stream handles;
- operation correlations;
- terminal receipts.

The renderer validates and stores those records; it does not fill missing values with `'1'`, `0`, or synthetic Tauri names.

### 3. One public façade does not imply fake host parity

Local, Electron, and Tauri factories may return the same application `BleManager` interface only under these rules:

- the trusted host bootstrap supplies the capability document and discovery model;
- `discovery.kind` remains `continuous-scan`, `system-chooser`, or `hybrid` rather than being inferred from JavaScript runtime names;
- renderer/webview code cannot select a backend, adapter, or support state unless the trusted host explicitly grants that operation;
- unsupported operations fail with the same normalized capability error as local managers;
- host-specific limits and evidence remain visible through capabilities;
- sharing a façade never permits Electron/Tauri to fabricate local attachment records, generations, write receipts, or lifecycle events;
- Web chooser semantics remain different from native scanning even though both produce `BlePeer` values.

The implementation may use different private adapters behind the façade. “Same public manager” means application vocabulary consistency, not one concrete class or lowest-common-denominator behavior.

### 4. One lifecycle event shape

Public connection events should carry:

```ts
interface ConnectionLifecycleEvent {
  readonly sequence: number
  readonly peer: PeerReference | null
  readonly connectionId: string
  readonly generation: string
  readonly previous: ConnectionState
  readonly current: ConnectionState
  readonly cause: ConnectionLifecycleCause
  readonly requested: boolean
  readonly observedAtMonotonicMs: number
}
```

Required states should distinguish at least:

- `connecting`;
- `connected`;
- `disconnecting`;
- `disconnected`;
- `waiting-for-peer` when supported;
- `suspended` only if it has precise semantics.

Required causes should distinguish:

- caller request;
- peer loss;
- connection failure;
- adapter unavailable/off/reset;
- permission change;
- backend reset;
- manager destruction;
- host/page termination;
- restoration/adoption;
- reconnect attempt replacement.

Local and IPC event ordering and generation semantics must be identical.

### 5. One notification value shape

Every host returns:

```ts
interface GattValueEvent {
  readonly value: Uint8Array
  readonly delivery: 'notification' | 'indication' | 'unknown'
  readonly observedAtMonotonicMs: number
  readonly sequence: number
}
```

Do not fold indication into a boolean `notify` property or return bare bytes on one host. If a backend cannot distinguish delivery type, report `unknown` and register a limitation.

### 6. One truthful write receipt

A write operation must not synthesize “confirmed” in the application layer. The host/core returns:

```ts
interface WriteReceipt {
  readonly terminal: OperationTerminalRecord
  readonly mode: 'with-response' | 'without-response'
  readonly commitState: 'confirmed' | 'accepted' | 'unknown' | 'not-started'
  readonly bytesSubmitted: number
}
```

Semantics:

- with-response success can generally be `confirmed` at the GATT operation level;
- without-response success is usually `accepted`, not proof the peripheral applied the value;
- cancellation/disconnect after dispatch may be `unknown`;
- pre-dispatch failure is `not-started`;
- long-write receipts retain per-chunk detail and aggregate this vocabulary.

### 7. Expand the built-in capability catalog

Create one canonical catalog with typed IDs. Keep open namespaced extensions, but built-ins should include at least:

#### Discovery and peers

- `discovery:continuous-scan`
- `discovery:system-chooser`
- `discovery:advertisement-watch`
- `peer:resolve-reference`
- `peer:known`
- `peer:system-connected`
- `peer:bonded`
- `peer:origin-authorized`
- `peer:restored`

#### Connections

- `connection:direct`
- `connection:when-available`
- `connection:rssi`
- `connection:effective-mtu`
- `connection:request-mtu`
- `connection:priority`
- `connection:parameters`
- `connection:phy`
- `connection:subrate`

#### Security

- `security:state`
- `security:pair`
- `security:cancel-pairing`
- `security:unpair`
- `security:custom-ceremony`

#### GATT

- `gatt:descriptors`
- `gatt:indications`
- `gatt:service-changed`
- `gatt:maximum-write-length`
- `gatt:long-write`
- `gatt:reliable-write`
- `gatt:write-without-response-readiness`
- `gatt:high-throughput-acquire`

#### Lifecycle/background

- `background:apple-restoration`
- `background:android-connected-device-service`
- `background:desktop-maintain-connection`
- `lifecycle:page-persistence`

Each catalog entry defines:

- ID and schema version;
- input/output types when invokable;
- state rules;
- required limits;
- required TCK suite/scenarios;
- minimum evidence level;

# PR 3 — Stable GATT object and property model

## Suggested PR title

`feat!: ship the stable GATT object and property model`

## Branch

`feat/4.0-gatt-object-model`

## Purpose

Turn the current precise but path-oriented GATT layer into an ergonomic, complete, generation-safe application model. Finish all GATT semantics that would otherwise force breaking changes after stable.

## This is not a revival of the 3.x mutable device graph

The object vocabulary is familiar, but the ownership and invalidation model remains the 4.0 model:

- `BlePeer` identifies or selects a remote peer; it is not an immortal connection-owning `Device`;
- `BleConnection` owns one lease and one connection generation;
- `GattDatabase`, `GattService`, `GattCharacteristic`, and `GattDescriptor` are immutable views created from one discovered database generation;
- every object stores the complete internal attachment/connection/database/occurrence path even though the application sees an ergonomic façade;
- reconnect, Service Changed, backend reset, host reload, or lease revocation makes prior objects stale;
- stale-object operations reject before native dispatch with `gatt.stale-handle`;
- objects never auto-connect, auto-rediscover, auto-resubscribe, or silently replace their hidden path;
- UUID equality alone never establishes object identity;
- no process-global mutable device-object cache is introduced;
- a convenience “current value” view, if provided, is derived from explicit read/write/subscription events and never treated as an authoritative hidden cache.

This preserves the RC1 path/generation guarantees while removing path boilerplate from normal application code.

## Complete GATT property vocabulary

The current characteristic model has read, two write modes, and notify. Stable 4.0 should preserve the full normalized property set relevant to a client:

```ts
interface GattCharacteristicProperties {

  readonly read: boolean
  readonly writeWithResponse: boolean
  readonly writeWithoutResponse: boolean

  readonly notify: boolean
  readonly indicate: boolean
  readonly extendedProperties: boolean
  readonly reliableWrite: boolean
  readonly writableAuxiliaries: boolean
```

Add a separate security/permission projection when a backend exposes it:

```ts

  readonly read: 'none' | 'encrypted' | 'authenticated' | 'authorized' | 'unknown'

```

Do not infer security requirements solely from an operation failure if the platform did not expose them. Preserve `unknown`.

Descriptor properties should include read/write and known security requirements where exposed.

## Occurrence and ambiguity rules

Duplicate service/characteristic/descriptor UUIDs are valid. Stable rules:

- occurrence indexes are zero-based within the parent and immutable for one database generation;
- `service(uuid)` succeeds only when exactly one match exists;
- multiple matches throw `gatt.ambiguous-path` with recovery metadata pointing to explicit selection;
- `service(uuid, { occurrence: 1 })` selects exactly one occurrence;
- `servicesByUuid` returns all matches in discovery order;
- object handles keep the complete internal path, not only UUID and occurrence;
- a new database generation invalidates every old object even when UUIDs and indexes happen to match.

## Discovery and caching rules

### Explicit discovery remains visible

`connection.discover()` returns a new `GattDatabase` snapshot/generation. Do not silently rediscover inside every characteristic operation by default; that can hide firmware/service changes and make operation latency unpredictable.

Convenience lookups may support:

```ts
connection.characteristic(serviceUuid, characteristicUuid, {
  discover: 'if-needed'
})
```

but the default high-level documentation should show explicit discovery.

### Cache policy

Define:

```ts
type GattCachePolicy =
  | 'use-current-generation'
  | 'rediscover'
  | 'platform-default'
```

Do not call undocumented Android cache-refresh APIs as a normal operation. Any diagnostic cache recovery added later must be capability-gated and clearly unsafe/limited.

## Service Changed behavior

Add a database change event:

```ts
interface GattDatabaseChangedEvent {
  readonly previousGeneration: string
  readonly reason: 'service-changed' | 'reconnect' | 'backend-reset' | 'manual-rediscovery'
  readonly affectedHandleRange: { start: number; end: number } | null
}
```

On service change:

1. mark the current database and every child handle stale;
2. close active subscriptions with a terminal reason that distinguishes service change from connection loss;
3. reject new operations on stale objects before backend dispatch;
4. emit one change event;
5. require or optionally trigger an explicit rediscovery according to caller policy;
6. never mutate existing service/characteristic objects into a new generation.

Where the platform provides only a generic “services invalidated” signal, `affectedHandleRange` is `null`.

## Notification and indication semantics

`GattSubscription.values` emits canonical `GattValueEvent` records from PR 2.

Subscription options:

```ts
interface GattSubscribeOptions extends OperationOptions {
  readonly delivery?: 'prefer-notification' | 'prefer-indication' | 'require-notification' | 'require-indication'
  readonly stream?: StreamPreset | AdvancedStreamOptions
}
```

Rules:

- if both notify and indicate are available, preference is explicit;
- a required mode rejects when unavailable;
- if the platform chooses and cannot be controlled, report the chosen/unknown delivery with a limitation;
- physical CCCD enable is shared/refcounted across logical consumers as current core semantics already require;
- no value is delivered before readiness;
- late values after unsubscribe/generation invalidation are quarantined;
- subscription object records its requested and effective delivery modes.

## Write semantics

### Normal write

```ts
interface GattWriteOptions extends OperationOptions {
  readonly response?: 'required' | 'not-required' | 'automatic'
}
```

Mapping:

- `required` → with response;
- `not-required` → without response, only if supported;
- `automatic` → prefer with-response for correctness unless a profile/option explicitly prefers throughput.

Do not silently downgrade a required response.

### Long write

The current core-emulated long write is valuable. Refine the public API:

- the characteristic chooses the current maximum write length for the requested mode;
- caller may cap chunk size but not exceed observed maximum;
- default long writes use with-response unless the caller explicitly chooses another protocol-safe mode;
- receipt preserves not-planned, planned, completed chunks, committed/unknown bytes, failed chunk, and terminal cause;
- no automatic retry after an unknown partial commit;
- optional inter-chunk pacing belongs to policy options and uses virtual-time tests;
- profile-specific framing remains application/profile responsibility.

### Reliable write

Expose reliable-write only when the backend has a real implementation and TCK. Do not label ordinary sequential chunking as ATT reliable write.

## Descriptor semantics

- discover all descriptors and preserve duplicate occurrences;
- CCCD may be visible in topology but normal direct writes to it reject with `gatt.cccd-managed`;
- subscription APIs own CCCD state;
- descriptor read/write returns owned bytes and exact receipts;

# PR 4 — High-level central workflow, canonical scan query, and lifecycle freeze

## Suggested PR title

`feat!: freeze the high-level central workflow and scan-query contract`

## Branch

`feat/4.0-high-level-central-dx`

## Purpose

Deliver the experience developers judge in their first hour: create, inspect adapter state, discover/select a peer, connect, discover GATT, exchange values, and clean up correctly. This PR also owns the **complete public scan-query semantics** so `4.0.0-rc.2` can honestly freeze the application vocabulary and behavior.

This is a **milestone PR** (see section 14.2): first-hour DX plus the scan-query contract. Use the same draft/phase/lettered-split controls as PR1.

PR9 will optimize query execution. It will not replace this contract. It must consume PR4 golden vectors; it must not invent a second matcher.

## Product principle

The safest path should also be the easiest path. Developers should not have to choose between convenience and deterministic cleanup, and they should not need to learn a second scan dialect after RC2.

## Discovery façade

### One manager, explicit discovery models

Expose:

```ts
interface BleDiscoveryInfo {
  readonly kind: 'continuous-scan' | 'system-chooser' | 'hybrid'
}
```

Methods:

- `scan()` requires continuous-scan capability;
- `choose()` requires system-chooser capability;
- `find()` is a scan-based helper and never opens a Web chooser implicitly;
- `knownPeers()` is a directory operation, not a scan substitute;
- host-specific types may narrow available methods, but trusted-host runtime capability remains authoritative.

This preserves honest Web semantics while keeping one manager vocabulary.

## Canonical `ScanQuery` v1 — frozen here

Replace RC1's narrow `ScanFilter` application shape before RC2. Keep any low-level RC1 filter only as an internal backend projection or remove it if no longer useful.

```ts
export interface ScanQuery {
  /** At least one clause must match. Omitted means match every observable peer. */
  readonly anyOf?: readonly ScanClause[]

  /** A matching exclusion removes the observation after positive matching. */
  readonly exclude?: readonly ScanClause[]
}

export interface ScanClause {
  readonly services?: {
    /** Match when any listed service is observed. */
    readonly any?: readonly UuidInput[]
    /** Match only when every listed service is observed. */
    readonly all?: readonly UuidInput[]
  }

  readonly names?: {
    readonly exact?: readonly string[]
    readonly prefixes?: readonly string[]
  }

  readonly manufacturerData?: {
    /** Match when any listed pattern matches. */
    readonly any?: readonly ManufacturerDataPattern[]
    /** Match only when every listed pattern has a matching observed entry. */
    readonly all?: readonly ManufacturerDataPattern[]
  }

  readonly serviceData?: {
    /** Match when any listed pattern matches. */
    readonly any?: readonly ServiceDataPattern[]
    /** Match only when every listed pattern has a matching observed entry. */
    readonly all?: readonly ServiceDataPattern[]
  }

  readonly rssi?: {
    readonly minimum?: number
    readonly maximum?: number
  }

  readonly connectable?: boolean
}

export interface ManufacturerDataPattern {
  readonly companyId: number
  readonly dataPrefix?: Uint8Array
  readonly mask?: Uint8Array
}

export interface ServiceDataPattern {
  readonly service: UuidInput
  readonly dataPrefix?: Uint8Array
  readonly mask?: Uint8Array
}
```

The exact exported names may be finalized during this PR, but the semantic structure and rules below are release-blocking.

### Frozen Boolean semantics

Document the same rules in JSDoc, generated API docs, the discovery guide, and executable tests:

1. `anyOf` clauses are ORed.
2. Fields within one clause are ANDed.
3. Values inside `services.any`, `manufacturerData.any`, `serviceData.any`, and `peers` are ORed within that field.
4. `names.exact` and `names.prefixes` form one OR set: either an exact-name match or a prefix match satisfies the names field.
5. Values inside `services.all`, `manufacturerData.all`, and `serviceData.all` are ANDed: every requested value/pattern must have at least one matching observed entry.
6. If both `any` and `all` are present for the same field, both constraints must hold.
7. `exclude` clauses are ORed and evaluated after the positive query.
8. Omitted `anyOf` means positive match-all; an explicitly empty `anyOf` is invalid.
9. An explicitly empty `exclude` is invalid; omit it when there are no exclusions.
10. A clause with no effective predicates is invalid.
11. Any supplied `any`, `all`, name, or peer list must be non-empty.
12. A field that is absent or unavailable does not match a predicate requiring that field.
13. RSSI comparisons use only the current normalized observation, never a cached value from a different packet.
14. PR4 has no peer-reference predicate. PR5 may add `ScanClause.peers` additively. When present, that list is ORed within the field, matching is exact within the reference's declared scope, and it never claims cross-platform physical identity. The Boolean algebra does not change.
15. All string matching is case-sensitive unless a future additive predicate explicitly says otherwise.
16. UUID inputs are canonicalized before comparison.
17. Masked byte comparison is `(observed[i] & mask[i]) === (prefix[i] & mask[i])` for every byte; mask and prefix lengths must match.
18. Multiple observed manufacturer/service-data entries are searched independently; one observed entry may satisfy more than one requested pattern only when it actually matches each pattern.

Changing any of these after RC2 is a breaking behavioral change.

### Query normalization authority

Implement one internal `normalizeScanQuery()` that:

- canonicalizes UUID inputs once;
- removes exact duplicates while preserving deterministic order;
- copies and freezes all byte patterns;
- validates company IDs from `0x0000` through `0xffff`;
- rejects empty names/prefixes;
- rejects NaN/infinite RSSI bounds and `minimum > maximum`;
- rejects empty clauses and supplied empty `any`/`all`/name/exclusion arrays whose meaning would be ambiguous;
- requires mask and prefix lengths to match;
- rejects a mask without a prefix;
- represents manufacturer/service presence by omitted prefix rather than an ambiguous empty byte array;
- validates peer-reference scope before physical radio work;
- returns an immutable normalized form;
- computes a stable semantic digest for scan sharing, hook restart avoidance, diagnostics, and differential tests.

The digest is not a persistent query ID, security token, or device identifier. Its canonical encoding and hash algorithm are versioned and tested so equivalent query input produces one digest independent of object insertion order.

### One pure canonical matcher

Implement one side-effect-free function over normalized data:

```ts
function observationMatchesScanQuery(
  query: NormalizedScanQuery,
  observation: NormalizedAdvertisementObservation
): boolean
```

This matcher is the **semantic oracle** for every host. PR4 initially may evaluate the entire query in the portable core after a safe broad native scan. PR9 may push predicates down only when differential tests prove equivalence.

No backend owns a second matcher. Web chooser filters may constrain which devices the browser offers, but selected observations still pass through the same normalized semantics for predicates the browser exposes.

## Public scan options frozen at RC2

```ts
export interface ScanOptions extends OperationOptions {
  readonly query?: ScanQuery
  readonly duplicates?: 'coalesced' | 'all'
  readonly delivery?: StreamDeliveryPreset | StreamDeliveryOptions
}
```

Defaults:

- omitted query: match every peer the host is permitted to expose;
- `duplicates: 'coalesced'` for application discovery;
- `delivery: 'balanced'`;
- raw advertisement records remain advanced/opt-in;
- no hidden platform-specific high-power mode.

`duplicates: 'coalesced'` is the **only** application current-view. Fields on that view may update. Do not describe it as simple first-seen deduplication. Do not add a second helper such as `scan.peers({ retentionMs })`.

Raw advertisement streams use `duplicates: 'all'` and remain available through `/advanced` for sensors/beacons that rely on every packet.

PR9 may add optional nested `observation` and `platform` fields additively, but it may not rename or reinterpret the fields above. A derived lost-peer timeout, if added, attaches to this same coalesced view.

### Scan session

```ts
interface ScanSession {
  readonly observations: AsyncIterable<AdvertisementObservation>
  readonly state: AsyncIterable<ScanStateEvent>
  stop(): Promise<CleanupRecord>
}
```

PR9 may add a read-only `plan` diagnostic property additively. Query matching must not depend on whether that property exists.

### Find helper

```ts
find({
  query,
  timeoutMs: 10_000,
  select: 'first' | ((peer) => boolean)
})
```

- returns a `BlePeer`;
- stops scan and preserves cleanup failures;
- rejects with `operation.timed-out` or caller abort;
- does not auto-connect;
- does not select an arbitrary peer when multiple candidates satisfy a non-deterministic selection rule;
- uses the exact same normalized query and matcher as `scan()`.

## Adapter and permission readiness

Add a high-level readiness helper:

```ts
await ble.adapter.waitUntilReady({ timeoutMs, signal })
```

It should:

- observe current snapshot atomically;
- resolve only when availability, authorization, and power permit the requested operation;
- reject with actionable `BleError` on terminal restriction;
- not request permission or power on Bluetooth itself;
- expose readiness requirements per operation (`scan`, `choose`, `connect`, `known-peers`).

Actual permission-request helpers arrive with Expo/native integration in PR10, but readiness and error vocabulary belong here.

## Safe resource scopes

Promote helpers to manager/connection methods and keep standalone functions only when useful for functional style.

### `withScan`

```ts
await ble.withScan(options, async scan => { ... })
```

### `withConnection`

```ts
await ble.withConnection(peer, options, async connection => { ... })
```

### `withSubscription`

```ts
await characteristic.withSubscription(options, async subscription => { ... })
```

Scope rules:

- cleanup always runs in `finally`;
- primary and cleanup failures are both retained;
- if only cleanup fails, throw a `BleCleanupError` or `AggregateError` with the cleanup record;
- if the callback aborts, cleanup still completes;
- cleanup uses a bounded internal deadline separate from the already-aborted user signal;
- no cleanup method is fire-and-forget.

Keep direct handles for long-lived app sessions.

## Optional explicit resource management

Implement `Symbol.asyncDispose` when the runtime supports it, but do not make it the only documented pattern because React Native/Hermes and build pipelines may differ. It calls the same stop/unsubscribe/release/destroy methods and is covered by compile/runtime fixtures.

# PR 5 — Known, connected, bonded, restored, and authorized peers

## Suggested PR title

`feat: add known, connected, bonded, restored, and authorized peers`

## Branch

`feat/4.0-known-peers`

## Purpose

Allow applications to reconnect to previously used devices without forcing a new scan, while accurately representing the very different “known device” concepts exposed by Apple, Android, Web Bluetooth, Windows, BlueZ, and desktop hosts.

This is one of the largest practical gaps between a technically complete BLE stack and a pleasant product library. Mature libraries expose system devices, saved IDs, bonded devices, or previously authorized browser devices because reconnecting by rescanning is slow, unreliable, and sometimes impossible in background scenarios.

## Product model: a peer directory, not one misleading list

Add a directory on the manager:

```ts
interface BlePeerDirectory {
  resolve(reference: PeerReference, options?: OperationOptions): Promise<BlePeer | null>
  known(options?: KnownPeerQuery): Promise<readonly BlePeer[]>
  connected(options?: PeerServiceQuery): Promise<readonly BlePeer[]>
  bonded(options?: KnownPeerQuery): Promise<readonly BlePeer[]>
  authorized(options?: KnownPeerQuery): Promise<readonly BlePeer[]>
  restored(options?: KnownPeerQuery): Promise<readonly BlePeer[]>
}
```

`BleManager` exposes:

```ts
readonly peers: BlePeerDirectory
```

Do not collapse all meanings into `getDevices()`. Each source has different guarantees.

## Additive scan predicate

PR5 adds one optional field to the frozen `ScanClause`:

```ts
readonly peers?: readonly PeerReference[]
```

Rules:

- this is a new optional field, not a reinterpretation of RC2 fields;
- the list is ORed within the field; the clause still ANDs across fields;
- matching is exact within the reference's declared scope;
- unknown/malformed references fail before radio work;
- the PR4 matcher is extended in one place and the golden-vector corpus gains peer cases;
- PR4 unknown-key rejection remains: any other new clause key still fails closed.

## Canonical source vocabulary

```ts
type PeerSource =
  | 'scan-observed'
  | 'app-reference'
  | 'system-connected'
  | 'system-bonded'
  | 'origin-authorized'
  | 'restored'
  | 'backend-cache'
```

Each returned peer includes all currently proven sources. A source is evidence about how the backend knows the peer, not proof of current reachability or physical identity.

Examples:

- Apple `retrievePeripherals(withIdentifiers:)` → `app-reference`;
- Apple `retrieveConnectedPeripherals(withServices:)` → `system-connected`;
- Android `getBondedDevices()` → `system-bonded`;
- Web `navigator.bluetooth.getDevices()` → `origin-authorized`;
- CoreBluetooth restoration → `restored` plus current connection state where known;
- BlueZ managed `Device1` object → `backend-cache`, with `system-bonded`/`system-connected` based on properties.

## Peer reference format

Use the PR1 versioned opaque reference:

```ts
interface PeerReference {
  readonly version: 1
  readonly backendId: string
  readonly scope: 'application' | 'origin' | 'system'
  readonly opaqueId: string
}
```

Rules:

- `opaqueId` is not documented as a MAC address, UUID, DeviceInformation ID, D-Bus path, or browser ID even if one backend encodes such data;
- reference serialization is deterministic JSON and round-trips without information loss;
- unknown future versions fail with `peer.reference-version-unsupported`;
- malformed references fail before backend dispatch;
- a reference for the wrong backend or origin returns a precise mismatch error, not `null`;
- `null` means a valid reference that the current backend can no longer resolve;
- references never contain secret keys or permission tokens;
- diagnostic redaction treats opaque IDs as identifiers.

A helper can exist:

```ts
encodePeerReference(reference): string
decodePeerReference(value): PeerReference
```

but normal persistence can use JSON.

## Query model

```ts
interface KnownPeerQuery extends OperationOptions {
  readonly sources?: readonly PeerSource[]
  readonly services?: readonly UuidInput[]
  readonly references?: readonly PeerReference[]
  readonly includeUnavailable?: boolean
}
```

Semantics:

- sources are ORed;
- service UUIDs mean any requested service unless an explicit `allServices` field is added;
- service filtering is native where possible and residual otherwise;
- `includeUnavailable` controls whether a valid known reference with no current device object is returned as a lightweight peer record;
- results are deduplicated by backend-scoped identity;
- source and metadata are merged deterministically;
- result ordering is documented: connected first, then restored, bonded/authorized, app references, backend cache, with a stable secondary key.

## Peer record state

Add a snapshot that distinguishes knowledge from connection:

```ts
interface BlePeerState {
  readonly reachability: 'reachable' | 'unreachable' | 'unknown'
  readonly connection: 'connected' | 'disconnected' | 'unknown'
  readonly bond: 'bonded' | 'not-bonded' | 'unknown' | 'unsupported'
  readonly lastSeenAtMonotonicMs: number | null
}
```

Do not infer `reachable` merely because a peer is bonded or returned by a system API.

## Connection by reference

`manager.connect(reference, options)` should resolve and connect without a scan when the backend supports it. Error behavior:

- wrong scope/backend → mismatch error;
- valid but unresolved → `peer.not-found` with `rescan`/`reselect-peer` recovery;
- permission revoked → authorization error with appropriate action;
- reference resolved but peer unavailable → connection error, not reference error;
- stale Web origin permission → choose/re-authorize recovery.

## Platform implementation requirements

### Apple mobile and desktop CoreBluetooth

Implement both official retrieval paths:

- retrieve by persisted peripheral identifiers;
- retrieve system-connected peripherals by service UUIDs.

Important semantics:

- service UUIDs are required for system-connected retrieval;
- a retrieved `CBPeripheral` object is not automatically connected to this manager;
- a UUID remains app/CoreBluetooth scoped, not a global hardware identity;
- restored peripherals preserve restoration provenance;
- returned peer records enter the same connection ownership/generation system as scanned peers.

### Android

Implement:

- bonded device snapshot when `BLUETOOTH_CONNECT` is granted;
- resolution of valid app references through the platform’s remote-device representation;
- connected GATT/system peer enumeration only where the public Android API accurately exposes it to this app and the result can be mapped without overclaiming;
- exact bond-state source and permission errors.

Do not assume every scanned random/private address remains resolvable after restart. Reference scope/limitations must state when identity stability is unknown.

Prepare an Android platform extension for Companion Device Manager association records, but keep association ceremony implementation in PR7/PR10 if it cannot remain focused here.

### Web Bluetooth

Use `navigator.bluetooth.getDevices()` only when available and register it as limited/experimental. Requirements:

- secure context and permissions-policy errors normalized;
- returned devices are `origin-authorized`, including out-of-range/off devices;
- no claim of cross-browser availability;
- `BluetoothDevice.forget()` maps later to permission revocation/unpair-like platform extension, not generic bond removal;
- a browser without `getDevices()` remains chooser-capable and reports known-peer unsupported.

### Windows/WinRT

Use DeviceInformation/AQS identity and pairing metadata:

- enumerate GATT-capable known devices;
- identify connected and paired state where public properties expose it;
- preserve the opaque DeviceInformation identity in `PeerReference`;
- do not treat paired as connected;
- avoid broad enumeration that causes unnecessary user-visible device access.

### BlueZ

Use the ObjectManager snapshot and `Device1` properties:

- connected → `system-connected`;
- paired/bonded → `system-bonded`;
- managed but neither → `backend-cache`;
- services-resolved/service UUID metadata where available;
- adapter identity included in opaque reference scope;
- removed D-Bus device objects invalidate backend-cache references without corrupting persisted references.

### Tauri

The current btleplug layer may not expose all native known-peer categories. Choose one of these, in order:

1. extend the Rust dispatcher with platform-specific boundaries that preserve the canonical contract;
2. expose truthful limited capability from btleplug’s current peripheral cache;
3. report unsupported.

Do not return a “known peers” list built only from this process’s prior scan and label it system-known.

### Electron

Direct selected desktop backend semantics pass through unchanged. Renderer reload does not erase persisted `PeerReference` values, but it invalidates live peer object handles.

## Optional watch API

Only add a watch stream if at least two first-party backends can implement meaningful changes:

```ts
peers.watch({ sources }): AsyncIterable<PeerDirectoryEvent>
```

Otherwise keep 4.0 snapshot-based and let connection/adapter/security streams report dynamic state. Do not add an API that mostly polls.

## Internal implementation plan

### A. Canonical directory merger

Create one pure merger that accepts backend peer records and:

- validates references;
- deduplicates;
- merges source/state/advertisement metadata;
- preserves the freshest timestamp without mixing clocks;
- applies residual service/source filters;
- returns deterministic ordering.

### B. Backend contract extension

Add optional methods/capabilities for:

- resolve references;
- known peers;
- connected peers;
- bonded peers;
- authorized peers;
- restored peers.

A backend may implement a combined primitive internally, but the public descriptors remain separate.

### C. No hidden persistence

The library creates persistable references but does not write AsyncStorage, UserDefaults, registry, filesystem, IndexedDB, or app databases. Persistence remains application-owned. This avoids retention/privacy policy inside the core.

### D. Reference invalidation and migration

References are versioned. Add a decoder table from day one. Version 1 is frozen at stable 4.0; future versions can migrate explicitly.

# PR 6 — Connection intents and deterministic reconnect supervision

## Suggested PR title

`feat: add connection intents and deterministic reconnect supervision`

## Branch

`feat/4.0-connection-intents-reconnect`

## Purpose

Add explicit semantics for “connect now” versus “connect when the peer becomes available,” then provide an opt-in, deterministic supervisor for retries, reconnection, rediscovery, and per-generation session setup.

The library should make reliable reconnect easy without hiding product policy inside `connect()`.

## Separate three concepts

### 1. One connection attempt

`manager.connect(peer, options)` creates one connection lease and one generation.

### 2. A backend connection intent

```ts
type ConnectionIntent = 'direct' | 'when-available'
```

- `direct`: attempt promptly and settle within deadline;
- `when-available`: ask the backend/OS to keep or queue an intent where supported; connection may enter `waiting-for-peer`;
- unsupported intent rejects before radio dispatch;
- intent is not the same as infinite retry in JavaScript.

### 3. A caller-owned supervisor

`ConnectionSupervisor` decides when to create/recreate attempts, based on explicit policy and gates.

Do not overload one boolean `autoConnect` with all three meanings.

## Connect options

```ts
interface ConnectOptions extends OperationOptions {
  readonly intent?: ConnectionIntent
  readonly transport?: 'le' | 'auto'
  readonly preferredPhy?: readonly BlePhy[]
}
```

Rules:

- `intent` defaults to `direct`;
- transport/PHY fields are capability-gated and may be moved under platform controls if they cannot remain portable;
- a direct attempt timeout terminates that attempt and releases native resources;
- `when-available` requires an explicit cancellation/lease lifetime and cannot be represented by a normal short timeout unless the caller sets one;
- connect never silently starts a reconnect supervisor.

## Supervisor API

```ts
interface ConnectionSupervisorOptions<Session> {
  readonly connection?: Omit<ConnectOptions, 'signal'>
  readonly retry: RetryPolicy
  readonly gate?: ConnectionGate
  readonly configure?: (connection: BleConnection) => Promise<Session>
  readonly disposeSession?: (session: Session) => Promise<void>
  readonly resetBackoffAfterConnectedMs?: number
}

interface RetryPolicy {
  readonly initialDelayMs: number
  readonly maximumDelayMs: number
  readonly multiplier: number
  readonly jitter: number
  readonly maximumAttempts?: number
  readonly maximumElapsedMs?: number
}
```

Supervisor methods/state:

```ts
interface ConnectionSupervisor<Session> {
  readonly events: AsyncIterable<ConnectionSupervisorEvent<Session>>
  readonly snapshot: ConnectionSupervisorSnapshot<Session>
  start(): void
  pause(reason?: string): Promise<void>
  resume(): void
  reconnectNow(): void
  stop(): Promise<CleanupRecord>
}
```

## Required deterministic state machine

```text
idle
  -> waiting-for-gate
  -> connecting
  -> configuring
  -> connected
  -> disconnecting
  -> backoff
  -> stopped
```

Terminal/fault transitions must distinguish:

- caller stop;
- maximum attempts/elapsed exceeded;
- invalid peer reference;
- permission permanently denied;
- adapter unsupported;
- pairing required;
- configure callback failure;
- connection loss;
- backend reset;
- cleanup failure.

A single monotonic attempt ordinal and connection generation identify events. Old attempt completions are quarantined.

## Gate model

Product policy remains caller-owned through a gate:

```ts
interface ConnectionGateContext {
  readonly attempt: number
  readonly adapter: AdapterState
  readonly lastError: BleError | null
  readonly lastDisconnect: ConnectionLifecycleEvent | null
}

type ConnectionGate =
  (context: ConnectionGateContext) =>
    | 'allow'
    | 'pause'
    | 'stop'
    | Promise<'allow' | 'pause' | 'stop'>
```

Use cases:

- app only reconnects during an active workout;
- pause on background unless FGS/restoration is configured;
- wait for user login;
- stop after battery/peripheral policy;
- external orchestration for multiple devices.

The supervisor supplies state; it does not decide business policy.

## Retry classification

Use PR2 recovery actions:

- safe transient connection failure → backoff;
- adapter off → wait for adapter state, do not burn attempts;
- permission not determined → pause for user action;
- permission denied/restricted → stop or wait according to gate;
- stale GATT → rediscover within the current connection, not reconnect immediately;
- bond lost/security failure → emit `repair` recovery and pause unless policy explicitly retries;
- invalid reference → stop;
- backend reset → recreate manager only if caller policy permits; supervisor itself should not replace the manager silently.

## Per-generation configuration

The `configure` callback is central. It runs once for each new connected generation and should be the supported place to:

- discover GATT;
- validate expected services/characteristics;
- enable notifications;
- read initial state;
- build a session object.

On disconnect/reconnect:

- prior session is disposed before the next is exposed;
- old subscriptions and GATT objects remain stale;
- configure failure closes/releases that connection before retry;
- application receives explicit configure-failed event/error;
- no subscription is magically reused across generations.

This is more honest and reliable than pretending characteristic handles survive reconnect.

## Backoff requirements

- use monotonic virtual time;
- full or decorrelated jitter must be deterministic under injected RNG;
- delay is capped;
- attempts reset only after configured stable-connected duration;
- adapter-off/permission-wait does not advance backoff;
- `reconnectNow()` cancels current backoff but not a live connect attempt unless explicitly documented;
- only one attempt may own the peer connection intent at a time;
- stopping during delay/connect/configure settles once and cleans all resources.

## Multi-client and multi-device behavior

The current ownership core already prevents connection stealing. Supervisor requirements:

- two supervisors for the same peer either join according to explicit ownership semantics or fail with `connection.already-owned`; they never unknowingly fight;
- one supervisor per peer is recommended;
- N peers reconnect independently;
- a manager-level optional concurrency limiter can bound simultaneous connects without serializing stable connected devices;
- fairness is deterministic under virtual time;
- no global singleton queue.

## Platform mappings

### Android

- `direct` maps to direct GATT connection;
- `when-available` maps to the platform auto-connect semantics only when the backend can prove them;
- current compile target remains aligned with Expo SDK 57/Android API 36; introduce an internal settings abstraction that can adopt API 37 `BluetoothGattConnectionSettings` later without changing public API;

### Apple

- notify-on-connect/disconnect options remain platform extensions/capabilities;
- app suspension and restoration limitations are explicit;
- restored connections enter a new adopted generation and run configuration according to policy.

### Windows

- use `GattSession.MaintainConnection` where `CanMaintainConnection` is true for `when-available` semantics;
- false default and indefinite waiting behavior are represented explicitly;
- release/stop sets maintain false and disposes session deterministically.

### BlueZ

- direct `Device1.Connect` behavior remains explicit;
- optional GATT profile auto-connect can support `when-available` only if ownership and release can be proven;
- otherwise use the portable supervisor with scan/known-peer resolution and report backend intent unsupported;
- do not rely on process-global BlueZ policy without cleanup.

### Web

- direct GATT connect is supported after chooser/known-device grant;
- `when-available` is limited and page-lifecycle-bound;
- supervisor may retry while the document is active but must stop/pause on page hidden/unload according to explicit policy;
- no background reliability claim;
- user gesture requirements for reauthorization are surfaced as user-action recovery.

### Tauri/Electron

- renderer/webview reload stops the old supervisor because it is application-owned;
- optional trusted-host durable intents would be a future feature, not silently created by renderer code;
- reload tests prove no orphaned native intent remains.

# PR 7 — Security, pairing, bonding, and ceremonies

## Suggested PR title

`feat: add security state, pairing, bonding, and ceremonies`

## Branch

`feat/4.0-security-pairing`

## Purpose

Expose the link-security and OS pairing capabilities developers expect, while refusing to pretend the platforms offer the same control. Pairing is a major competitive gap and a common source of opaque GATT failures.

## Separate terminology

Stable docs and types must use these words precisely:

- **pairing:** exchange/authentication ceremony that establishes keys or authorization;
- **bonding:** durable storage of keys/relationship;
- **encryption:** current link protection state;
- **authentication:** whether MITM/authenticated security is known;
- **authorization:** app/OS permission to use Bluetooth or a protected attribute;
- **association:** Android Companion Device Manager relationship, distinct from a BLE bond.

Do not use “paired” as a universal synonym for connected, authorized, or bonded.

## Public security façade

```ts
interface BleSecurity {
  state(peer: BlePeer | PeerReference, options?: OperationOptions): Promise<PeerSecurityState>
  watch(peer: BlePeer | PeerReference): AsyncIterable<PeerSecurityEvent>
  pair(peer: BlePeer | PeerReference, options?: PairOptions): Promise<PairResult>
  cancelPairing(peer: BlePeer | PeerReference): Promise<PairCancelResult>
  unpair(peer: BlePeer | PeerReference, options?: OperationOptions): Promise<UnpairResult>
}
```

`BleManager` exposes:

```ts
readonly security: BleSecurity
```

## Security state model

```ts
interface PeerSecurityState {
  readonly bond: 'bonded' | 'not-bonded' | 'bonding' | 'unknown' | 'unsupported'
  readonly encryption: 'encrypted' | 'not-encrypted' | 'unknown' | 'unsupported'
  readonly authentication: 'authenticated' | 'unauthenticated' | 'unknown' | 'unsupported'
  readonly secureConnections: 'yes' | 'no' | 'unknown' | 'unsupported'
  readonly pairingPossible: boolean | null
  readonly measuredAtMonotonicMs: number
  readonly limitations: readonly Limitation[]
}
```

Never turn absence of measurement into `not-encrypted` or `not-bonded`. `unknown` and `unsupported` remain distinct.

## Pair API

```ts
interface PairOptions extends OperationOptions {
  readonly transport?: 'le' | 'auto'
  readonly protection?: 'system-default' | 'encrypted' | 'authenticated'
  readonly ceremony?: 'system' | PairingAgent
}
```

Default is system-mediated. Requirements:

- system UI remains owned by the OS where appropriate;
- pairing resolves only after a terminal bond/pair result, not when the request is merely accepted;
- cancellation settles exactly once;
- repeated pair on an already bonded peer returns an explicit `already-bonded` result, not a fake new ceremony;
- re-pair/repair is a distinct result/policy;
- timeout/cancel does not remove an existing valid bond;
- pair may establish a temporary encrypted connection depending on platform, but it does not return a normal app connection lease unless explicitly documented.

## Result model

```ts
type PairResult =
  | { outcome: 'paired'; state: PeerSecurityState }
  | { outcome: 'already-paired'; state: PeerSecurityState }
  | { outcome: 'repaired'; state: PeerSecurityState }
  | { outcome: 'rejected'; reason: string | null }
  | { outcome: 'cancelled' }
```

Failures that are programmer/protocol errors still reject. User cancellation/rejection can be a result when the platform distinguishes it reliably; choose one consistent rule and document it.

## Custom ceremony infrastructure

Where the OS allows application participation, expose a narrow agent:

```ts
interface PairingAgent {
  onChallenge(challenge: PairingChallenge): Promise<PairingResponse>
}

type PairingChallenge =
  | { kind: 'confirm'; peer: BlePeer }
  | { kind: 'confirm-passkey'; passkey: number; peer: BlePeer }
  | { kind: 'display-passkey'; passkey: number; peer: BlePeer }
  | { kind: 'provide-pin'; peer: BlePeer }
  | { kind: 'provide-passkey'; peer: BlePeer }
```

Safety requirements:

- challenge contains no native object;
- responses are one-shot and deadline-bound;
- passkeys preserve leading-zero display rules;
- PIN/passkey values are redacted from logs/traces;
- late response after cancellation is ignored and cleared;
- only one active ceremony owns a peer;
- UI thread requirements are handled in the host adapter;
- custom ceremony is capability-gated and never emulated by intercepting undocumented broadcasts.

It is acceptable for 4.0 to implement custom ceremony only on Windows/BlueZ and system ceremony on Android, with Apple/Web unsupported or implicit.

## Unpair semantics

Unpair means removing durable OS pairing information where a public supported API exists.

- Windows: `UnpairAsync`;
- BlueZ: adapter `RemoveDevice`/bond removal semantics, with explicit warning that backend-cache device object is also removed;
- Web: `forget()` is origin permission revocation, **not** generic unpair; expose it under an origin-authorization/platform extension or map to a clearly named `forgetAuthorization`, not `unpair`;
- Apple: no app-controlled unpair; report unsupported and direct user to system settings only when appropriate;
- Android: do not use hidden reflection APIs. If the supported SDK lacks a public remove-bond API, report unsupported. Never ship reflection as stable behavior.

## Pairing triggered by protected GATT access

Many platforms initiate pairing implicitly when a protected characteristic is accessed. Stable behavior:

- the original GATT operation receives a security-specific error or may continue after OS ceremony according to platform;
- security events reflect bond/encryption changes;
- `BleError.recovery` can include `repair` or `pair`;
- the library does not automatically call `pair()` and replay a write unless caller explicitly uses a helper;
- provide an opt-in helper:

```ts
withRequiredSecurity(peer, requirement, async () => ...)
```

This helper inspects state, pairs if explicitly allowed, then runs the callback once. It must not blindly replay an uncertain write.

## Android Companion Device Manager extension

Android recommends Companion Device Manager for a streamlined association/pairing UI and reduced location-permission burden. Add an Android-specific extension if it can be implemented cleanly:

```ts
ble.platform.android?.companion.associate(request)
ble.platform.android?.companion.associations()
ble.platform.android?.companion.disassociate(id)
```

Requirements:

- association is never mislabeled as BLE bond;
- activity-result lifecycle is resilient to configuration changes;

### Android

Each measured value should carry:

- Android MTU request validates 23–517 or the platform/current contract range;
- Apple OS-negotiated values are observed rather than requested;
- Windows `GattSession.MaxPduSize` is not mislabeled as a requestable ATT MTU;
- Web reports unsupported/unavailable honestly;

## Connection parameters and subrate

Observation can include when available:

- interval;
- peripheral latency;
- supervision timeout;
- subrate factor/mode;
- connection event length or platform-specific detail in extension fields.

## Per-connection GATT operation scheduler

A high-quality BLE library needs deterministic operation ordering. The current core already tracks operation settlement; make scheduling explicit and documented:

- one serialized queue per physical connection for operations the platform requires serialized;
- independent logical callers retain cancellation/deadline identity;
- cancelled queued operations are removed before dispatch;
- cancellation after dispatch follows exact uncertainty rules;
- disconnect/service change/backend reset settles every queued/in-flight operation once;

- operations on different connections proceed concurrently;
- queue limits are bounded with explicit overflow/backpressure errors;
- TCK proves order, fairness, cancellation, and cleanup.

Do not expose a public “command queue” singleton. The scheduler is a connection invariant.

- edge events as an optimization;

```ts
  readonly effect: 'performance-only' | 'field-unavailable' | 'host-restriction'
}
```

Each first-party backend implements an internal planner:

```ts
interface BackendScanPlanner<NativeFilter> {
  plan(query: NormalizedScanQuery, context: ScanPlanningContext): BackendScanExecutionPlan<NativeFilter>
}
```

A backend plan contains:

- native filter/configuration accepted by that host;
- residual normalized query evaluated by the shared PR4 matcher;
- predicates unavailable because the platform does not expose required data;
- proof that native pushdown is exact or a safe superset;
- expected callback/bridge load classification;
- capability and OS-version limitations;
- redacted diagnostics with no raw advertisement payloads.

No backend writes a second predicate evaluator.

## Additive public scan options

PR9 may add optional fields without changing PR4 defaults:

```ts
export interface ScanOptions extends OperationOptions {
  readonly query?: ScanQuery
  readonly duplicates?: 'coalesced' | 'all'
  readonly delivery?: StreamDeliveryPreset | StreamDeliveryOptions

  readonly observation?: {
    /** Derived timeout on the coalesced current-view. Omitted preserves PR4 behavior. */
    readonly reportLostAfterMs?: number
    readonly includeRawAdvertisement?: boolean
  }

  /** Explicit host extension. Ignored behavior is forbidden. */
  readonly platform?: ScanPlatformOptions
}
```

Rules:

- omitted `observation` preserves PR4 behavior;
- raw advertisement bytes remain excluded by default and are capability-gated;
- `reportLostAfterMs` is portable derived behavior, not a claim that the OS emits a lost event;
- platform options are discriminated and validated before radio work;
- unsupported platform options reject with typed capability/argument errors; they never silently no-op;
- adding these optional fields must not alter the semantic digest of the query itself—execution-policy digesting is separate.

## Derived lost-peer timeout on the coalesced view

Do not add a second current-view API. When `reportLostAfterMs` is configured, the existing coalesced view may emit a derived lifecycle record:

```ts

  | { readonly kind: 'observed'; readonly peer: DiscoveredPeer }
  | {
      readonly kind: 'lost'
      readonly peer: PeerReference
      readonly lastObservedAt: number
      readonly derivedAt: number

```

Requirements:

- uses monotonic time;
- driven by the same virtual timer authority as operation deadlines;
- no wall-clock timers in tests;

- lost timers are cancelled on scan stop/destroy;
- coalescing state is byte/item bounded;
- the default remains disabled;

2. Residual matching uses the frozen canonical matcher.

## Configuration principles

### 1. One restoration identity, not five application strings

The current `iosNativeProtocolRestoration` object asks the app for identifier, namespace, epoch, client ID, and host-session scope. Those values protect the native protocol, but they should not all be user-authored application API.

The trusted plugin/native host derives the restoration domain from exactly:

- a versioned derivation-domain constant, for example `ubm-restoration-v1`;
- the trusted application identifier (`CFBundleIdentifier` on Apple; equivalent trusted application ID only where another host later needs the same concept);
- the application-facing restoration ID;
- the optional explicit restoration generation, with one documented default.

From that domain, the native authority derives the internal restoration identifier, namespace, client identity, and host-session scope using one specified deterministic algorithm. JavaScript receives opaque derived values during bootstrap and never authors or recomputes them.

The derivation must **not** include:

- per-launch randomness;
- manager instance ID;
- wall-clock time;
- package/library version;
- app build number;
- OS version;
- device model.

Ordinary app and library updates therefore retain restoration compatibility. Changing the bundle/application ID, restoration ID, or explicit generation intentionally creates a new domain. The app supplies only the stable restoration name and an optional generation when it deliberately wants to invalidate old state.

#### Deterministic derivation contract

Lock one cross-language derivation specification in an ADR and golden-vector file. A recommended exact contract is:

1. Validate `restoration.id` as an ASCII token matching `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`.
2. Validate `generation` with the same character set and a maximum of 64 bytes; default to the literal `1`.
3. Read the trusted application identifier from native application metadata; never accept an application ID from JavaScript options.
4. Encode the domain input as length-prefixed UTF-8 fields to avoid delimiter ambiguity; every `len(...)` below is the unsigned byte length of the following UTF-8 field:

```text
magic = UTF8("ubm-restoration-v1")
input = magic
      || U32BE(len(applicationId)) || UTF8(applicationId)
      || U32BE(len(restorationId)) || UTF8(restorationId)
      || U32BE(len(generation))    || UTF8(generation)
root = SHA-256(input)
```

5. Derive each internal value with a distinct label:

```text
derive(label) = BASE64URL_NO_PADDING(
  SHA-256(root || 0x00 || UTF8(label))
)

nativeRestoreIdentifier = applicationId + ".ubm." + prefix(derive("restore"), 22)
restorationNamespace    = "ubm-ns:"     + derive("namespace")
restorationClientId     = "ubm-client:" + derive("client")
restorationHostScope    = "ubm-host:"   + derive("host")
```

6. Treat the derivation-domain string as a persistence-format version. Changing the algorithm requires an explicit migration decision; it must never happen because the npm package version changed.
7. Store/configure only the application-facing restoration ID and generation. The native host derives internal values before constructing the central manager and returns opaque identity in bootstrap.
8. Use the same golden vectors in the Expo plugin tests, Swift/Kotlin/native host tests, and TypeScript bootstrap validation. Do not maintain independent example values.

The exact output prefixes may be adjusted before implementation, but the properties—length-prefixed canonical input, SHA-256, domain separation, labeled derivation, no randomness, and versioned golden vectors—must remain.

No compatibility alias for the five-field RC1 object is necessary because there are no consumers to preserve.

The plugin must:

- reject unknown keys;
- reject invalid discriminated-union combinations;
- reject empty permission strings/IDs/channel names;
- reject restoration without iOS central background mode;

|---|---|

## 10.6 Before / after: the RC1 Heart Rate loop

**RC1 (do not copy forward):** `deadline()`, `defaultScanDelivery()`, `scanUntil` + verbose `filter` / `sharing`, `withConnection` + `resolveCharacteristicPath` + `firstNotification`.

**4.0.0 target (names may settle; this shape is the freeze):**

```ts
import { createReactNativeBleManager } from 'unified-ble-manager/react-native'
import { HEART_RATE_SERVICE, parseHeartRateMeasurement } from 'unified-ble-manager/profiles/heart-rate'

const ble = await createReactNativeBleManager()
const abort = new AbortController()
const op = { signal: abort.signal, timeoutMs: 20_000 }

try {
  const peer = await ble.find({
    query: { anyOf: [{ services: { any: [HEART_RATE_SERVICE] } }] },
    timeoutMs: 20_000,
    signal: abort.signal,
    select: 'first'
  })

  await ble.withConnection(peer, op, async connection => {
    const gatt = await connection.discover(op)
    const measurement = gatt.service(HEART_RATE_SERVICE).characteristic('2a37')
    const subscription = await measurement.subscribe({ ...op, delivery: 'balanced' })
    try {
      for await (const event of subscription.values) {
        consume(parseHeartRateMeasurement(event.value))
        break
      }
    } finally {
      await subscription.unsubscribe()
    }
  })
} finally {
  await ble.destroy()
}
```

Cleanup failures must still be checked (`destroy()` / `unsubscribe()` return a cleanup record, or throw `BleCleanupError` / aggregate). Do not fire-and-forget `destroy()`.

# 13. Performance, memory, and reliability budgets

BLE performance depends heavily on radio interval, packet length, peripheral firmware, operating-system scheduling, and host hardware. Therefore, stable 4.0 should not publish one fake universal throughput number. It should enforce three kinds of budgets:

1. **semantic invariants** that must always hold;
2. **relative regression gates** on controlled benchmarks;
3. **scenario-specific live envelopes** recorded with exact hardware/software.

## 13.1 Semantic invariants

These are release blockers regardless of benchmark machine:

- no unbounded application or IPC stream;
- no unbounded pre-JS/pre-renderer event ingress;
- no late value after a terminal stop/remove/release for the same generation;
- no stale generation callback mutates current state;
- no cross-connection head-of-line blocking from the shared portable scheduler;
- no one-consumer backpressure blocks another consumer;
- no silent drop: every dropped/replaced item is represented by overflow counters/notices according to policy;
- no write-without-response submission when readiness/queue capacity says unavailable;
- no timer/listener/lease/handle retained after successful final cleanup;
- no raw host import starts a radio or permission prompt;
- no diagnostic path copies payload bytes unless the configured diagnostic mode requests it;
- no renderer/webview receives observations rejected by trusted-host residual filtering when that path is enabled;
- no operation's timeout is extended by nested helpers;
- no retry loop runs on wall-clock sleeps in deterministic tests.

## 13.2 Relative regression policy

For stable benchmark environments:

- compare median, p95, allocation count, and retained-memory end state;
- block a greater than 10% median or p95 regression unless the PR includes an ADR, raw samples, and a correctness/feature justification;
- block any statistically clear unbounded growth regardless of percentage;
- compare like-for-like machines/runtimes only;
- keep at least the last stable and current release-candidate baselines;
- rerun noisy native benchmarks enough times to report confidence/range rather than one sample;
- never optimize by weakening validation, ownership, bounds, or error truth.

## 13.3 Controlled benchmark scenarios

### Core/TypeScript

- normalize operation options;
- normalize/plan/match scan queries;
- merge advertisement/current-peer observations;
- create and invalidate GATT object graphs;
- route duplicate UUID occurrences;
- deliver bounded streams under no pressure and overflow pressure;
- reconnect supervisor virtual-time transitions;
- capability lookup and diagnostics projection;
- trace redaction and support-bundle creation.

### Native protocol and IPC

- control-record encode/decode;
- binary payload transfer at 20, 182, 244, 512, 4 KiB, 64 KiB, and maximum permitted sizes;
- sustained notifications at 100, 500, and 1,000 events/second in deterministic/IPC harnesses;
- four and eight independent streams;
- event acknowledgement path;
- Tauri trusted-host residual rejection ratio;
- Electron renderer reload/lease cleanup;
- malformed/oversized record rejection cost;
- no-copy/copy counts where instrumentation permits.

These are software pipeline rates, not promises that a BLE peripheral/OS can generate them physically.

### GATT scheduler

- one connection with 10,000 queued operations;
- four connections with fair independent queues;
- cancellation at queue head/middle/tail;
- write-with-response latency;
- write-without-response readiness bursts;
- long-write 1 KiB, 64 KiB, and maximum configured payload;
- service-change invalidation during queue load;
- disconnect/destroy while saturated;
- final resource counters and retained memory.

### Live fixture envelopes

For each physical run, record:

- peripheral/firmware;
- host hardware/radio;
- OS/runtime;
- negotiated connection parameters where observable;
- MTU/PDU/write length;
- event/packet/payload rate;
- duration;
- drops/overflows/retries;
- CPU/memory/energy observations where available;
- exact package/crate/native artifact digest.

The release gate is that the library does not introduce unexplained loss, unfairness, or unbounded growth at the fixture's declared rate—not that every host hits the same rate.

## 13.4 Multi-device quality bar

Stable 4.0 should prove the architecture with:

- at least four deterministic concurrent connections on every core/TCK run;
- eight deterministic concurrent connections for scheduler/fanout stress;
- at least two physical concurrent peripherals on each platform receiving a multi-device live claim;
- independent reconnect state machines;
- independent GATT queues/subscriptions;
- shared adapter scan arbitration without starvation;
- per-peer diagnostics/counters;
- manager destroy that settles all peers once;
- no connection-generation collision or cross-peer handle use.

Do not publish a universal maximum-device count. Expose backend/OS limits when known and let capability limitations/evidence describe tested counts.

## 13.5 Memory quality bar

Use before/after and steady-state evidence rather than one universal byte ceiling.

Required assertions:

- bounded queue allocations match configured capacities within known overhead;
- copied BLE payload ownership is explicit;
- coalesced discovery retains at most one current record per tracked peer plus bounded metadata;
- peer directory does not retain raw historical advertisements;
- stopped sessions release query/matcher/timers;
- disconnected generations release GATT graphs once no consumer references them;
- support bundle/trace generation releases temporary buffers;
- long soak reaches a steady-state envelope after warm-up;
- repeated create/destroy loops do not trend upward beyond runtime cache noise;
- native resource instruments/weak references prove callbacks and managers are collectible where practical.

## 13.6 Reliability quality bar

A backend cannot earn reliability qualification without:

- declared scenario duration;
- declared hardware/OS matrix;
- reconnect/background/reload cycles appropriate to that host;
- no fatal native error or application crash;
- no missed terminal/resource leak;
- bounded overflow accounting;
- exact artifact binding;
- explicit limitations and revalidation cadence.

A one-time successful connect is a live vertical slice, not reliability proof.

# 14. Engineering and merge discipline across the 12 PRs

## 14.1 Sequential integration

These PRs intentionally build on one another. Use this flow:

1. branch PR1 from current `main`/RC1;
2. merge PR1 after all gates;
3. rebase/branch PR2 from updated `main`;
4. continue sequentially;
5. publish only the planned release candidates after PR4, PR8, PR10, and PR11;
6. branch PR12 from the exact RC5 main state.

Avoid maintaining twelve long-lived stacked branches with repeated conflict resolution and stale assumptions. An implementation agent may prepare designs/tests ahead, but each merge-ready PR should target the latest `main` and include only its defined scope.

## 14.2 PR size management and milestone-PR decision

The owner intentionally prefers twelve numbered merge PRs. PR1, PR2, PR4, and PR10 are **milestone PRs**, not claims that each diff will be small. PR4 is a milestone because it now owns first-hour DX **and** the scan-query contract.

That choice is workable for a solo maintainer using implementation/review agents, but the review-risk criticism is valid. Apply these mandatory controls:

- open the PR as draft at the first failing contract/type tests;
- keep the advertised public contract incomplete only on the draft branch, never on `main`;
- organize 6–15 atomic commits into named review phases;
- record a reviewer checkpoint after each phase before starting the next high-risk phase;
- keep generated output in separate commits from authored schemas where practical;
- run focused gates after each phase and the full gate before merge;
- never merge a stable public method whose backend/IPC behavior is knowingly fabricated or deferred;
- publish an RC only after the whole numbered milestone is complete.

| Milestone PR | Phase A | Phase B | Phase C | Phase D |
|---|---|---|---|---|

# 19. Decisions locked by this plan

1. **Break RC1 now.** There is no external compatibility obligation worth preserving.
2. **RC2 is the stable portable runtime vocabulary and scan-semantics freeze.** Expo configuration freezes at RC4 and Tauri installation/CLI at RC5; none may reopen portable semantics.
3. **Application API and backend SDK are different products inside one package.** The root is simple; rigor remains underneath.
4. **One public manager/resource vocabulary spans local, browser, Electron, and Tauri, but capabilities remain host-issued and honest.** IPC implementation types are not application concepts; shared vocabulary never means fake parity.
5. **No renderer/webview fabricates identity or success.** Trusted hosts issue generations and receipts.
6. **Generation-bound GATT objects are the normal API; immutable portable paths remain advanced/internal.** They are not immortal 3.x-style device objects and never silently reconnect or rediscover.
7. **Discovery modes are explicit.** Continuous scan, chooser, known peers, and connection intents are not silently substituted.
8. **Reconnect is opt-in caller-owned supervision.** The library provides the deterministic engine and OS intent mapping, not a hidden product policy.
9. **Pairing, bonding, encryption, authentication, association, and origin authorization remain distinct.**
10. **MTU, PDU, maximum write length, readiness, priority, PHY, parameters, and subrate remain distinct request/observation concepts.**
11. **Scan Boolean semantics, normalization, digest, and canonical matcher freeze in PR4/RC2.** PR9 adds only differential-equivalent planning and additive execution controls.
12. **Expo uses development builds and one restoration ID.** Restoration identity is deterministic from trusted app ID + restoration ID + generation; `createExpoBleManager()` remains a thin React Native composition; Expo Go is not supported.
13. **Android foreground work is explicitly leased.** No silent always-on service.
14. **Tauri uses a published crate and granular permissions.** The npm package/crate/protocol handshake before radio work.
15. **Stable package SemVer does not imply equal backend support labels.** Evidence remains exact and honest.
16. **No feature after PR11.** PR12 qualifies and releases.

# 21. Final recommendation

Start PR1 immediately from the current RC1 main branch and stop adding new convenience features to the provisional root API. The most valuable work now is not one more BLE method; it is making sure every later method lands on the right stable vocabulary.

The critical sequence is:

1. simplify and freeze the app contract, including canonical scan semantics;
2. unify trusted-host semantics;
3. finish the GATT/lifecycle foundation;
4. add known peers, reconnect, security, controls, and rich discovery;
5. make Expo and Tauri genuinely excellent;
6. prove installation, testing, diagnostics, performance, live behavior, and release integrity;
7. publish `4.0.0` only from the exact qualified artifacts.

Executed in order, these twelve PRs should leave Unified BLE Manager with a rare combination:

- easier first use than typical native BLE wrappers;
- deeper central functionality than most JavaScript libraries;
- safer ownership and lifecycle semantics than convenience-focused competitors;
- stronger cross-platform truth than static feature matrices;
- a real Expo and Tauri product experience;
- deterministic app testing without hardware;
- and support claims that can survive serious technical scrutiny.

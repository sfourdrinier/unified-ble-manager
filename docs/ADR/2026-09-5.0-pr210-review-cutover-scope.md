# ADR: PR210 review (R01–R16) cutover + distribution scope

**Status:** Draft (interview in progress; nothing below is accepted until explicitly confirmed)
**Date:** 2026-09-17
**Context:** Agent handoff review `PR210_AGENT_HANDOFF.md` (R01–R16) against lane HEAD `b114bec2`.
Fix agents are executing the non-scope findings in parallel; this record settles only the
product-scope forks. Fix ownership and per-finding evidence live in the coordinator ledger
(`/tmp/PR210_LEDGER.md`), not here.

## D1: R01+R03 production-cutover scope — DECIDED (a)
User decision (2026-09-17, session): "5.0 is full cutover, tested so (a)".
All five hosts (RN, Android, Apple, Tauri, Node/Electron) flip to Rust authority in this
program, each proven by acceptance tests — no host left on legacy default, no opt-in-only
seams as the production story. Engineering order still respects prerequisites (P1 lifecycle
fixes land before their host's flip is proven), but the scope is the full set, not a subset.

## D2: Apple + Android native distribution/build policy — DECIDED modified (b)
User decision (2026-09-17, session): "Build the Rust native artifacts in
unified-ble-manager's own CI/release workflow. Ship the verified Apple
XCFramework and Android native libraries with the npm package. Normal app
consumers should not need Rust installed. Retain an explicit source-build
mode for developing UBM itself." Full decision text supplied by the user in
session (covers Apple AND Android; pod-vs-Expo-module and source-vs-prebuilt
are separate decisions).

Normative points:
1. One npm package. UBM CI builds the Rust artifacts from authoritative
   source; normal consumers receive VERIFIED prebuilts and need no Rust
   toolchain. Prefer bundling artifacts in the npm tarball (measure size
   before any split/CDN design).
2. Apple: Rust static libraries inside an XCFramework, consumed through the
   EXISTING pod integration. Qualify iOS device/simulator + tvOS
   device/simulator explicitly; keep architecture promises precise. Static
   linkage stays; XCFramework signing becomes a controlled release step.
3. Android: Rust JNI `.so` files through the EXISTING Gradle library
   (`src/main/jniLibs/<ABI>` standard location; no duplicate packaging
   paths). No separate Maven publication required for the npm/RN/Expo path.
   Real 16 KB page-size compatibility checks on shipped libraries.
4. Framework wrappers (Swift/Kotlin adapters, generated binding source,
   RN-specific native integration) stay SOURCE compiled in the consumer —
   prebuild Rust, not the entire host integration. Binding technology
   (JNI/UniFFI) unchanged.
5. JS integration UNCHANGED: keep `unified-ble-manager/react-native` and
   `unified-ble-manager/expo` as two entrypoints into one native
   implementation. No Expo Modules API rewrite, no second BLE runtime as
   part of this decision. Native host owns the authoritative Rust runtime;
   RN and Expo attach clients (no competing radio owners).
6. Build modes are EXPLICIT configuration: `prebuilt` (default for
   published packages; missing/incompatible artifacts = actionable error,
   never silent source build, never legacy fallback) vs `source`
   (contributors; same canonical builders as CI; stale outputs rejected,
   not silently reused). No `.git` inference, no tool-sniffing.
7. Apple source mode: explicit repo-owned preparation producing the
   framework BEFORE local pod integration (prepare_command does not run
   for `:path` pods — cannot serve local consumers). Android source mode:
   fix the Linux-only NDK linker path; real tested macOS + Linux
   contributor flows; outputs isolated by ABI/profile/identity.
8. Identity: extend `scripts/release/generate-build-fingerprint.js` (no new
   manifest zoo). The build record must bind source/dependency digest +
   binding-schema/ABI revision + features + target/arch + deployment
   minimum + compiler/SDK identity + artifact hashes. "Built from" must be
   proven, not just "present together". Native bootstrap identity verified
   before sessions/BLE. Release pipeline: declared inputs → canonical
   build → bindings+identity → verification → packed candidate → clean
   consumer acceptance.
9. Same-repo release flow; no external artifact feed, no separate
   native-version scheme. Same-repo release archive may be a secondary
   vehicle carrying the SAME immutable artifacts.
10. D1 unchanged: full authoritative Rust cutover on all five hosts, proven
    through acceptance tests.

Work packages (do not reopen the migration): (i) common distribution
contract (fingerprint/identity, prebuilt/source modes, metadata alignment);
(ii) Apple packaging (podspec + builder, valid variants, no
prepare_command reliance for normal local-pod consumers); (iii) Android
packaging (build.gradle + builder, explicit mode, host portability, ABI +
page-size verification); (iv) candidate/release integration (CI-built
artifacts staged before pack, extended tarball checks); (v) RN/Expo
acceptance (one native owner, both entrypoints against production binding).

Acceptance scenarios: clean consumer WITHOUT Rust (bare RN + Expo, build
and invoke core); contributor source build (edit Rust fn, rebuild, prove
changed identity loads); negative artifact tests (removed/substituted/
corrupted/mismatched artifacts fail clearly pre-BLE); lifecycle ownership
(multiple clients, recreation, background/foreground, teardown — no
competing owners); actual platform proof (real factory + binding +
authoritative Rust, not typechecks/echo symbols).

Consequence for in-flight R05/R06 work: the hardened
`ios/build-rust-core.sh` (lane f76b948d) remains the CANONICAL source
builder used by CI artifact production and contributor source mode; the
podspec/prepare_command consumer path must move to prebuilt consumption
per this decision. Android's `.git`-inferred mode and NDK host path are
now tracked defects under work package (iii).

## D3: R01 production binding producer — DECIDED (a) native session facade

R01 (RN flip to the shared Rust core) was blocked: no production
`ReactNativeRustCoreBinding` producer exists — only test fakes produce
`{openSession}`; the control spec has no session/op surface; JNI is
consumed by Kotlin only, never bridged to JS; iOS has no core TurboModule.
Flipping the factory default without a producer would brick every real
call, so the producer precedes the flip.

Decision (user, 2026-09-17): (a) build a native session facade — a
TurboModule per platform (`UnifiedBleRustCore`: Kotlin over the JNI
cdylib, Swift over the UniFFI XCFramework) implementing exactly the F01
seam (`openSession(owner)` → `{contractRevision, invoke, close}`), with a
Codegen spec, revision admission, and emulator/simulator acceptance —
then flip the RN factory default to it (R01), keeping `expo.ts` a thin
composition over the RN factory (one native owner per platform).

Rejected: (b) thin JS bridge over the existing native adapters (keeps the
legacy execution path — not a cutover, violates D1); (c) deferring R01 to
5.1 (ships 5.0 on legacy RN — violates the decided D1 full cutover).

Work package (sequenced): binding-producer (spec + Kotlin + Swift +
Codegen + JVM/XCTest seams + device proofs) → R01 flip (factory default +
`expo.ts` composition + acceptance) → D2(v) entrypoint acceptance → R16
regression matrix.

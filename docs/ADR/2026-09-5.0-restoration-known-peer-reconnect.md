# ADR: 5.0 known-peer restoration on iOS and Android

**Status:** Accepted design baseline; iOS fresh-manager direct-reconnect
qualification remains open
**Date:** 2026-09-19
**Issue:** [#212](https://github.com/sfourdrinier/unified-ble-manager/issues/212)

## Decision

Restoration reconnects **directly to devices this app already connected to**,
and nothing else. No background scanning for unknown devices, no
`PendingIntent` scan fallback. The same app code, the same public events, and
the same vocabulary names run on iOS and Android; a platform or OS version
that cannot do it reports `capability.unsupported` with a reason, never a
fake.

The two platform observations feed one public surface:

- **iOS:** CoreBluetooth state restoration. The app opts in with
  `background.ios.restoration` (`{id, generation}` in the Expo plugin, or the
  `restoration` manager option); the trusted native host derives the
  `CBCentralManagerOptionRestoreIdentifierKey` value (`restoreIdentifierKey`)
  from it. When the system terminates the app, it relaunches it on a BLE
  event and delivers the restored peripherals through `willRestoreState`. The
  library announces them as `restored` peers (`peers.restored`,
  `restoration-received`, `restoration.claim()`), and the app may reconnect
  directly with the durable restored `PeerReference` before it replays
  subscriptions through the public API. Apple does not implement Android's
  `when-available` intent. The shared driver now accepts the restored
  `PeerReference` for direct reconnect; the physical fresh-manager path still
  needs qualification.
- **Android:** known-peer reconnect through `connectGatt(autoConnect = true)`
  (the existing `intent: 'when-available'`), armed per associated peer with
  Companion Device Manager device presence
  (`CompanionDeviceManager.startObservingDevicePresence`,
  `CompanionDeviceService.onDeviceAppeared`, API 31+). Presence builds on the
  existing `associateCompanion` capability: the app associates, persists the
  association's peer reference, and observes that peer. When the device
  reappears, the system binds the library's `CompanionDeviceService` (added to
  the manifest by the Expo config plugin), which reconnects directly and
  surfaces the **same** `restored` peers, `restoration-received` event, and
  vocabulary names as iOS.

A known peer is recorded as a **persisted peer reference**: the companion
association (`associationId`, `peerId`, device address) the app obtained and
persisted, plus the library-persisted presence appearance record the service
writes when no session is alive. Observation is per explicitly armed peer;
`presence.unobserve` stops the callbacks. Nothing is scanned, nothing is
remembered implicitly.

## Consequences and gates

- Public API (extended, not reinvented): `peers.restored`,
  `restoration.claim()`, `connect` with `when-available` (Android;
  Apple refuses it as `capability.unsupported` because CoreBluetooth has no
  `autoConnect` — the OS itself holds pending connects), and the new
  `presence.observe` / `presence.unobserve` session services (Expo
  `presence` surface). Legacy iOS restoration identities
  (`restoration-connection-{n}`, pinned by rust-core-legacy-parity tests)
  are kept.
- Events: `restoration-received` on both platforms, the `restored` drain
  record, and a `restoration-received` row in
  `src/backend-contract/event-vocabulary.ts` (regenerated table, fixture,
  and Rust mapping coverage). Web, desktop, tvOS, and Android below API 31
  report `capability.unsupported` with a reason for presence observation.
- Capabilities: `peer:restored` is registered on the React Native Rust-core
  route for both platforms (Apple: needs the configured restoration
  authority; Android: needs a presence wake or a live attach), and
  `state:presence-observation` is registered (Android: needs API 31+ and an
  association; Apple: unsupported, restoration arrives through
  `willRestoreState`).
- Native gates: Rust `ubm-mobile` session tests, Kotlin `rustcore` tests
  (observer, service, store), the Swift harness (restore → connect →
  subscribe → values on a restored link), TS provider/public/Expo tests,
  plugin tests for the manifest service, and the shared `restoration`
  example scenario on both phones.
- Physical proof (owner, later): iOS — terminate from the Mac with
  `xcrun devicectl device process terminate` (never a user force-quit, which
  disables restoration); Android — `adb shell am kill` (a force-stop
  disables presence wake). Procedure in `docs/BACKGROUND.md`.

## Rejected alternatives

- **Background scanning / `PendingIntent` scans for unknown devices:**
  rejected — it reconnects to devices the app never connected to, against
  the owner principle and the privacy posture (no silent radio work).
- **A separate Android-only restored API:** rejected — AGENTS.md requires
  one vocabulary; Android emits the same `restoration-received` event and
  the same peer records as iOS, with the platform detail underneath in
  `platform`.
- **Automatic reconnect / subscription resume without an app call:**
  rejected — the package owns no reconnect policy; adoption and replay
  happen through the public `connect` / `subscribe` calls, so the app stays
  in control and nothing reconnects silently.
- **The API 36 `ObservingDevicePresenceRequest` API:** rejected for 5.0 —
  the `String`-address `startObservingDevicePresence` (API 31+) reaches
  every device the feature supports, including the API 31–35 majority; the
  newer request type stays an option for a later version.

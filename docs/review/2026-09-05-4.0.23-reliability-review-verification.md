## Per-finding evidence

### BLE-01 — confirmed, keep P1

`admit_caller_correlation` (`native/tauri/src/btleplug_dispatcher.rs` 3289–3310) rejects when `operations.len() + completed.len() >= 256` as `protocol.violation` / `tauri.correlation-window`. Replay is a separate code (`tauri.correlation-replay`). `route` admits every command except `operation.cancel`. `kind == "release"` bypasses this path. Native tests encode the coupling as intended; no test that cleanup still admits after >256 unique completed routes.

### BLE-02 — confirmed, keep P1

`connect` reserves `peer_owners` before `peripheral.connect()`. Late/missing caller compensates without inserting into `caller.connections`. Failed compensation leaves the reservation; the `Peripheral` drops with the stack frame. `release` / `settle_caller` only walk adopted connections. Existing tests lock in reservation retention, not recoverability.

### BLE-03 — confirmed, keep P1

`fail_scan_stream` (2856–2893) takes `caller.scan`, clears `scan_owner`, then `adapter.stop_scan().await.ok()`. `start_scan` admits whenever `scan_owner` is `None`. Contrast: `settle_caller` keeps ownership until stop is `Ok`.

### BLE-04 — confirmed, keep P2

`fail_subscription_stream` (2896–2926) checks lease, removes the subscription, awaits unsubscribe, then on error `callers.get_mut(caller_key)` and reinserts with no generation check. Adjacent: `stop_scan` / `unsubscribe` also mutate the current caller after await without re-checking lease.

### BLE-05 — confirmed, keep P2

`unified-ble-core.ts` stale-admission scan/connect: `captureCleanup` then `throw`. `captureCleanup` has no ledger. Adapter-watch already inserts before late-stop and keeps pending acquisition for destroy. No test named `scan-stale-admission-release` / `connect-stale-admission-release`.

### BLE-06 — confirmed, keep P2

`rediscoverGatt` joins `this.discoveries` then, after the wait, always starts replacement discovery. `invalidateDatabase` / `markInvalid` run synchronously before the next waiter’s `assertCurrent`. Stale-result rejection, not a demonstrated double-install.

### BLE-07 — confirmed, keep P2

`PublicScanSessionController.accept` always writes observations and events. Observation stream is allocated in the constructor; event queues are per subscriber. `overflowPolicy: 'error'` on the unused observation queue calls `terminateFromOverflow` and `requestStop('overflow')`. Default `balanced` / `drop-oldest` does not terminate. IPC public scan has no `events` view, so this coupling is in-process only.

### BLE-08 — confirmed, keep P2

`IpcPublicScanSession` only mutates state in `stopInternal`. Host `kind: 'terminal'` finishes delivery; it does not project into `scanState`. In-process `finish()` closes iterators without `requestStop` / `scanState` update. The review’s causal link is slightly wrong: IPC does not call `PublicScanSessionController`. Same state-machine gap, two adapters.

### BLE-09 — confirmed, keep P2

`stopBluezPhysicalDiscovery` / `stopBluezPhysicalSubscription` wait for global `Discovering=false` / `Notifying=false` after successful Stop*. Timeout → `release-failed` and retained logical ownership. In-memory harness always flips those properties, so two-client coexistence is untested.

### BLE-10 — confirmed, keep P1

`subscribeBluez` enablement rejection handler deletes `physicalSubscriptions` unless destroying. The waiter’s `catch` starts `beginBluezPhysicalRemoval` only when the map still points at that physical. FIFO: delete runs first. Destroy later iterates only the map.

### BLE-11 — confirmed, keep P2

`SetDiscoveryFilter`, `StartDiscovery`, and `ConnectDevice` are bare `await`s. Later `waitForBluezBoolean` / presence waits are bounded. Scan abort during `'starting'` only sets `stopRequested`. Existing lifecycle tests advance `now` inside already-completed method callbacks.

### BLE-12 — confirmed, keep P2

`discoverBluezAddressDevice` reuses any existing `scanGroup` and waits for the device object. Native `SetDiscoveryFilter` `UUIDs`/`Pattern` can exclude the target. Timeout is bounded.

### BLE-13 — confirmed, keep P1

`OwnedCoreBluetoothProtocolRadio.swift` 609–614: first pending read wins `didUpdateValueFor`. `read` does not inspect notify state. Apple uses this callback for both reads and notifications. Android (`onCharacteristicRead` vs `onCharacteristicChanged`) and WinRT (`ReadValueAsync` vs `ValueChanged`) do not share this fusion. **Adjacent:** `native/electron/corebluetooth/src/addon.mm` 1600–1629 is the same first-wins pattern. No 4.x contract forbids read-while-notifying.

### BLE-14 — confirmed, keep P2

`classifyAndroidNotificationRegistrationFailure` sets `isLinkLoss=true` with no GATT status. Dispatcher remaps that to protocol `"connectionLost"`. Android tests assert this mapping. JS `nativeOperationFailure` maps `connectionLost` to `connection.lost` recovery vocabulary; subscribe failure does not emit the native `connectionLost` event or close the GATT generation.

### BLE-15 — confirmed, keep P1

Native `StartNotify` registers `ValueChanged` before awaiting CCCD write. TS `emitWinRtNotification` returns unless `physical.state === 'ready'`. Readiness is set after native completion; logical consumers are created after that. Fake `startNotify` already stores the handler while the gate is pending; tests only emit after subscribe resolves.

### BLE-16 — confirmed, keep P1

`invalidateWinRtPhysicalSubscription` awaits cancellation and `physical.enablement` with no deadline. `disconnectInternal` awaits that invalidation before `startNativeDisconnect`. Native `StartNotify` holds `gatt_mutex` across CCCD write, which can also stall later cleanup. Vertical-slice tests wait for late enable and always `enable.resolve()`.

### BLE-17 — partial, keep P2

Android `cancelPairing` never reads `_options`; it awaits native cancel then the pair result. WinRT awaits unbounded `requestCancellation()`, then bounds native `cancelPairing` via the dispatcher, then unbounded `await active.result`. Public result is correctly `cancelOutcomeForPairResult` (must not invent `cancelled` from an ack). **Adjacent:** BlueZ `cancelPairing` also ignores `_options`.

### BLE-18 — confirmed, keep P2

`watchAdapterState` samples once and registers a stream. Transitions only come from `refreshAttachmentAvailability`, which runs on attach / `currentAdapterState` / chooser. Navigator boundary has no `availabilitychanged` listener. Web Bluetooth spec defines the event. CoreBluetooth, Android, WinRT, BlueZ, and IPC (500 ms poll) all push live changes. Existing web test encodes stale-until-probe.

## Extra findings (not in the original claim list)

1. **Electron/Node CoreBluetooth shares BLE-13.** `addon.mm` `didUpdateValueForCharacteristic` completes `pendingReadAt` / `pendingRead` before notify handlers.
2. **BlueZ `cancelPairing` shares BLE-17’s `_options` ignore.** Same waiter pattern as Android.
3. **BLE-04-class post-await mutation also exists on Tauri `stop_scan` and `unsubscribe`.** Lease is not re-checked after the native await.
4. **BLE-07 kill-the-scan path is policy-gated.** Default `balanced`/`drop-oldest` silently drops the unused observation buffer; `lossless-bounded` / custom `error` terminates the physical scan.
5. **BLE-14 is locked in by Android unit tests** that assert registration failure → `"connectionLost"` / `isLinkLoss=true`. Fixing it requires updating those tests, not only the radio.

## What this does *not* decide

- Implementation order beyond the reviewer’s P1 cluster (BLE-01–03, 10, 13, 15, 16).
- Whether read-while-notifying should be rejected, exposed as value-update semantics, or a coordinated stop/read/restore.
- Whether BlueZ should widen a live scan, return scan-conflict, or require ConnectDevice.
- Hardware frequency of enablement-time WinRT ingress, CoreBluetooth notification-before-read-response, or `setCharacteristicNotification` returning false on a live link.
- Whether to add a web `availabilitychanged` listener, a poll fallback, or both.

Those are product/contract decisions for the fix PRs.

## Recommended response posture

Treat the review as accepted except BLE-17’s WinRT half, which is a bounded-dispatcher gap rather than a total ignore of `_options`.

Do not disable replay checks, inflate all buffers, swallow cleanup errors, or report cancellation acknowledgement as physical completion.

Must-fix before treating 4.0.23 as stability-qualified:

- BLE-01 admission vs replay capacity split, with reserved cleanup admission.
- BLE-02 orphan connect compensation owner.
- BLE-03 stopping-scan owner until native stop settles.
- BLE-10 BlueZ post-accept enablement failure keeps `StopNotify` owner.
- BLE-13 explicit iOS (and Electron) read-vs-notify contract.
- BLE-15 bounded enablement-time notification staging.
- BLE-16 bounded disconnect vs in-flight enablement.

Then the P2 lifecycle/public/BlueZ/Android/Web cluster.

Group related fixes into narrowly scoped PRs with failing-before/passing-after regression evidence. Do not merge or release from this verification pass.

## Exact findings and regression specifications

### BLE-01 — Valid Tauri traffic exhausts replay retention and blocks ordinary resource cleanup (P1)

**Files:** [`native/tauri/src/btleplug_dispatcher.rs`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/native/tauri/src/btleplug_dispatcher.rs); [`src/ipc/public-manager.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/ipc/public-manager.ts)

**Symbols:** `admit_caller_correlation`, `remember_completed_correlation`, `route`, `IpcAdapterWatchOwner`.

**Trigger:** Complete more than the available 256 correlation slots inside the 30-second retention window, using legitimate reads, writes, state queries, or control calls.

**Root cause:** Admission counts both active operations and recently completed correlations against MAX_CORRELATIONS. A completed request therefore keeps consuming admission capacity until its replay-retention TTL expires. Normal routed cleanup commands use this same admission path. Sharing a 500 ms poll reduces one source of demand but leaves the coupling in place.

**Impact:** A healthy session can report protocol.violation/tauri.correlation-window under ordinary traffic. Scan stop, unsubscribe, and connection cleanup can then fail at admission, making recovery harder.

**Proposed fix:**

1. Separate the bound on physically active operations from replay detection. Use a protocol-aware replay window or another bounded scheme that does not treat all recently completed requests as active capacity.
2. Reserve bounded admission capacity for cleanup/control operations. Continue validating identities and replay rules on that path.
3. Expose legitimate capacity exhaustion as a resource/backpressure outcome, not as malformed or replayed traffic. Do not disable replay protection or merely increase the polling interval again.

**Required regression checks:**

- Run more than 256 unique completed routed requests inside 30 seconds; cleanup must remain usable.
- Repeat with the shared adapter watcher active and several independent GATT consumers.
- Replay an old correlation and verify rejection remains intact.

**Qualification:** The separate renderer lease-release endpoint bypasses ordinary route admission. This finding does not claim every destroy/release route is blocked.

### BLE-02 — Late Tauri connection compensation can retain a reservation without a retryable resource (P1)

**Files:** [`native/tauri/src/btleplug_dispatcher.rs`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/native/tauri/src/btleplug_dispatcher.rs)

**Symbols:** `connect`, `compensate_unowned_connection`, `apply_compensation_outcome`, `release`, `settle_caller`.

**Trigger:** A native connect completes after its caller/lease is gone or replaced, and the compensating disconnect fails.

**Root cause:** The compensation path can preserve peer_owners while the newly connected peripheral was never adopted into caller.connections. The normal release path walks adopted connections, or returns released when no caller exists. A reservation is retained, but the resource needed to retry its disconnect is not represented in that cleanup path.

**Impact:** The peripheral can remain connected or reserved while future connect attempts are denied. The resource cannot be recovered through the normal caller-owned cleanup loop.

**Proposed fix:**

1. Create an explicit orphan/pending-connection cleanup owner containing the peripheral, peer ID, caller lease/generation, and retry state before awaiting compensation.
2. Keep the reservation and cleanup owner together. Release both only after physical release is proven.
3. Make caller release and later connection admission drive or observe retained orphan cleanup.

**Required regression checks:**

- Delay connect; revoke the caller; complete native connect; fail the first compensating disconnect.
- Assert an inspectable pending cleanup resource remains and the next cleanup retry releases it.
- Verify an old cleanup result cannot release a reservation held by a newer generation.

**Qualification:** This is a specific late-adoption failure path, not a claim that all disconnect failures are forgotten.

### BLE-03 — Tauri scan-stream failure forgets ownership before native stop settles (P1)

**Files:** [`native/tauri/src/btleplug_dispatcher.rs`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/native/tauri/src/btleplug_dispatcher.rs)

**Symbols:** `fail_scan_stream`.

**Trigger:** An event-delivery failure terminates a scan stream, while the native stop is delayed or fails.

**Root cause:** fail_scan_stream takes the scan out of caller state, clears scan_owner, and only then awaits adapter.stop_scan(). The stop outcome is discarded with .ok().

**Impact:** A failed stop leaves a physical scan without retry ownership. A concurrent new scan can be admitted before the old stop completes, allowing the old stop to affect the new scan.

**Proposed fix:**

1. Keep the exact scan owner in a stopping state until its native stop completes.
2. Serialize adapter scan admission against that stop; do not reopen admission when only the logical stream has ended.
3. Retain and surface failed cleanup so it can be retried.

**Required regression checks:**

- Force event-sink failure while stop_scan is deferred, then request a second scan.
- Verify the second scan is not admitted over the outstanding stop.
- Fail stop once and confirm the original resource is still available for retry.

### BLE-04 — Old Tauri subscription cleanup can be reinserted into a replacement lease (P2)

**Files:** [`native/tauri/src/btleplug_dispatcher.rs`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/native/tauri/src/btleplug_dispatcher.rs)

**Symbols:** `fail_subscription_stream`.

**Trigger:** A failed stream removes its subscription and awaits native unsubscribe. The same window acquires a replacement lease before unsubscribe rejects.

**Root cause:** The function checks expected_lease before the await. Its failure branch then looks up the caller by key and reinserts the old subscription without checking the lease/generation again.

**Impact:** A replacement caller can inherit an old subscription cleanup record, mixing resource generations and producing incorrect cleanup/accounting.

**Proposed fix:**

1. Repeat the lease/generation comparison after the native await before mutating caller state.
2. When the old lease no longer exists, retain the resource in an old-generation quarantine, not in the replacement caller.
3. Audit equivalent post-await reinsertion paths using the same ownership rule.

**Required regression checks:**

- Defer unsubscribe; replace the caller lease; reject the old unsubscribe.
- Assert the new caller has no old subscription and the old resource still has a retry owner.

### BLE-05 — Core late scan/connect rollback failure is observed but not retained by the manager (P2)

**Files:** [`src/core/unified-ble-core.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/core/unified-ble-core.ts); [`src/core/core-lifecycle-observer.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/core/core-lifecycle-observer.ts)

**Symbols:** `scan`, `connect`, `captureCleanup`.

**Trigger:** Backend acquisition resolves after core admission has become stale, and the compensating lease stop/release fails.

**Root cause:** The stale-admission branch calls captureCleanup once and throws the original admission error. captureCleanup records/normalizes the result but does not register the unadopted lease as a retryable manager-owned resource.

**Impact:** The manager loses a direct cleanup retry path for the acquisition. Backend-wide cleanup may sometimes recover it, but manager-scoped release is not sufficient, especially with a borrowed backend.

**Proposed fix:**

1. Track pending acquisitions from dispatch until adoption or confirmed compensation.
2. Move late resources into a retained cleanup ledger when rollback fails, using the same principle already applied to adapter-watch acquisition.
3. Keep public cancellation prompt while making subsequent release attempts retry retained resources and report cleanup truth.

**Required regression checks:**

- Destroy or invalidate admission during a pending scan/connect, then resolve the native lease.
- Fail lease.stop/release once; invoke manager cleanup again and verify it retries that exact lease.
- Repeat with a borrowed backend and assert unrelated backend resources are unaffected.

**Qualification:** The claim is loss of manager-scoped retry ownership, not proof that every first-party backend loses its own record.

### BLE-06 — Concurrent rediscovery callers can fail on a snapshot invalidated by another waiter (P2)

**Files:** [`src/core/unified-ble-core.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/core/unified-ble-core.ts); [`src/core/core-discovery.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/core/core-discovery.ts); [`src/core/core-gatt-handles.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/core/core-gatt-handles.ts)

**Symbols:** `rediscoverGatt`, `discoverCoreGattDatabase`, `invalidateDatabase`.

**Trigger:** Two rediscoverGatt calls wait for the same already-pending discovery.

**Root cause:** After awaiting that discovery, each caller asserts that the returned database is current. The first resumed caller starts replacement discovery and synchronously marks that database invalid. The next waiter can then fail its assertCurrent check instead of joining or orderly queuing behind the replacement.

**Impact:** Concurrent refresh/service-change work can surface an avoidable stale-handle failure even though a valid replacement operation is already under way.

**Proposed fix:**

1. Coordinate initial discovery and rediscovery through a per-connection single-flight or serialized generation transition.
2. After any wait, re-read the currently registered operation instead of asserting against an obsolete shared result.
3. Define whether concurrent rediscovery requests coalesce or queue, and install a replacement only if its connection/database epoch still matches.

**Required regression checks:**

- Hold initial discovery pending; start two rediscovery calls; resolve the initial discovery.
- Verify the documented coalescing/serialization policy with no accidental stale-handle rejection.
- Add service-change and caller-cancellation interleavings.

**Qualification:** Closer tracing shows a stale-result rejection path. An accounting leak or two successfully installed replacement databases was not established and is not claimed.

### BLE-07 — Consuming only discovery events can overflow the unused observations queue (P2)

**Files:** [`src/public/ble-manager.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/public/ble-manager.ts)

**Symbols:** `PublicScanSessionController.accept`, `PublicScanSessionController.start`, `PublicScanEventBroadcast`.

**Trigger:** Consume session.events but not session.observations, using duplicates=all and an error-on-overflow delivery policy.

**Root cause:** Either view starts the shared pump, but accept always writes to both observationStream and eventBroadcast. The unconsumed observation queue fills; its terminated result causes terminateFromOverflow for the whole scan.

**Impact:** A consumer keeping up with every requested event can nevertheless have its scan terminated by a different, unused output view.

**Proposed fix:**

1. Allocate/feed output queues only while those views have subscribers, or define an explicitly bounded startup replay policy.
2. Separate subscriber-local overflow from shared physical scan termination.
3. Ensure presence/lost-event tracking does not require retaining an unused raw observation queue.

**Required regression checks:**

- Consume only events at full speed and emit more than the observation item/byte budget.
- Repeat consuming only observations and then both views with different consumer speeds.
- Verify the explicitly documented overflow policy for the subscribed view still applies.

### BLE-08 — IPC scan state stays active after the source terminates (P2)

**Files:** [`src/ipc/public-manager.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/ipc/public-manager.ts); [`src/public/ble-manager.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/public/ble-manager.ts)

**Symbols:** `IpcPublicScanSession`, `PublicScanSessionController.finish`.

**Trigger:** The host closes or fails the scan stream without an explicit caller stop().

**Root cause:** IpcPublicScanSession updates its local active state through its stop path. The public scan controller finishes its views on source termination but does not project that terminal back into the session state.

**Impact:** The iterator/UI can show an ended stream while session state still reports active, confusing stop/restart logic and status displays.

**Proposed fix:**

1. Give scan state one authoritative terminalization path used by host terminal events, source failures, cleanup completion, and explicit stop.
2. Preserve the terminal cause and distinguish ended delivery from any remaining physical cleanup obligation.
3. Update state independently of whether a consumer is currently iterating the stream.

**Required regression checks:**

- Send source-failed, connection-lost, and ordinary terminal events without calling stop().
- Assert the public session is no longer active and can be cleaned up/restarted correctly.
- Repeat with no iterator attached.

### BLE-09 — BlueZ cleanup requires global inactivity instead of release of this client session (P2)

**Files:** [`src/backends/bluez/bluez-scan-runtime.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/bluez/bluez-scan-runtime.ts); [`src/backends/bluez/bluez-subscription-runtime.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/bluez/bluez-subscription-runtime.ts)

**Symbols:** `stopBluezPhysicalDiscovery`, `stopBluezPhysicalSubscription`.

**Trigger:** Another D-Bus client remains scanning or subscribed after this backend successfully calls StopDiscovery/StopNotify.

**Root cause:** Successful stop calls are followed by waits for global Discovering=false or Notifying=false. BlueZ sessions are shared: another client can legitimately keep those properties true after this client has released its session.

**Impact:** False cleanup failures and retained logical ownership can block otherwise valid restart/resubscribe operations when another BLE app is running.

**Proposed fix:**

1. Treat successful release of this caller’s session as its ownership evidence; do not require unrelated clients to become idle.
2. Keep bounded waits and retryable ownership for actual native call failures, missing objects, and uncertain outcomes.
3. Model global adapter/characteristic activity separately from locally owned sessions.

**Required regression checks:**

- Use two independent simulated/real D-Bus clients; keep one active after the other stops.
- Assert local cleanup succeeds with global Discovering/Notifying still true.
- Verify the remaining client is not disrupted.

**Primary platform references:** [Documentation 1](https://bluez.readthedocs.io/en/latest/adapter-api/); [Documentation 2](https://bluez.readthedocs.io/en/latest/gatt-api/)

### BLE-10 — BlueZ notification enablement failure can remove the owner before compensation (P1)

**Files:** [`src/backends/bluez/bluez-subscription-runtime.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/bluez/bluez-subscription-runtime.ts)

**Symbols:** `subscribeBluez`, `createBluezPhysicalSubscription`, `beginBluezPhysicalRemoval`.

**Trigger:** StartNotify has succeeded, but the subsequent enablement confirmation fails or times out.

**Root cause:** An enablement rejection handler deletes the physical subscription from physicalSubscriptions. The waiting consumer’s catch starts orphan cleanup only when the map still points to that physical subscription. The earlier deletion makes this condition false.

**Impact:** A rejected subscribe can leave the native notification session enabled without the normal retryable StopNotify owner.

**Proposed fix:**

1. Distinguish failure before physical enablement from failure after native acceptance.
2. Keep post-acceptance failures in an enabling-failed/cleanup-pending record and compensate through StopNotify.
3. Delete the physical record only once compensation or authoritative device removal proves release.

**Required regression checks:**

- Make StartNotify succeed and then fail/timeout the confirmation stage.
- Assert StopNotify is attempted despite the rejected subscription.
- Fail that stop once and verify a later cleanup attempt still owns and retries it.

### BLE-11 — Some BlueZ acquisition awaits do not enforce the caller deadline (P2)

**Files:** [`src/backends/bluez/bluez-scan-runtime.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/bluez/bluez-scan-runtime.ts); [`src/backends/bluez/bluez-connection-runtime.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/bluez/bluez-connection-runtime.ts)

**Symbols:** `startBluezScan`, `materializeBluezAddressDevice`.

**Trigger:** SetDiscoveryFilter, StartDiscovery, or ConnectDevice stalls beyond a short caller deadline or after caller cancellation.

**Root cause:** These native method promises are directly awaited before later property/admission waits. A deadline on the later wait does not bound the earlier native await; scan cancellation during start records stop intent rather than necessarily settling the public start immediately.

**Impact:** Caller-facing scan/address-connect operations can outlive their supplied deadline, with confusing cancellation and delayed recovery.

**Proposed fix:**

1. Apply deadline/abort admission to every asynchronous acquisition phase, including the native method call itself.
2. Separate prompt public settlement from continuing native work; retain that work until its late result is adopted or compensated.
3. Do not use a bare Promise.race that forgets a later successful native allocation.

**Required regression checks:**

- Independently stall each native method with a fake clock and a short deadline.
- Verify prompt public terminal, retained native ownership, and late-success cleanup.
- Ensure a second scan/connect cannot bypass a still-owned pending acquisition.

### BLE-12 — BlueZ address-connect fallback can wait on an incompatible existing scan (P2)

**Files:** [`src/backends/bluez/bluez-connection-runtime.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/bluez/bluez-connection-runtime.ts); [`src/backends/bluez/bluez-scan-runtime.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/bluez/bluez-scan-runtime.ts)

**Symbols:** `discoverBluezAddressDevice`, `materializeBluezAddressDevice`.

**Trigger:** ConnectDevice is unavailable and address discovery falls back to scanning while an unrelated filtered scan already exists.

**Root cause:** The fallback reuses the existence of a scan group without verifying that the native scan plan can observe the requested device. A target excluded by that scan’s filters may never materialize.

**Impact:** Known-address connection can time out only when another discovery flow is active, producing a difficult-to-explain cross-flow failure.

**Proposed fix:**

1. Check scan-plan compatibility before relying on a current physical scan.
2. Coordinate a safe temporary widening/restoration of the native scan, or return an explicit scan-conflict/unsupported outcome.
3. Keep every existing consumer’s residual filtering and ownership intact.

**Required regression checks:**

- Disable ConnectDevice in the boundary; start a native scan restricted to service A; request an address advertising only service B.
- Verify the fallback either finds the target through coordinated scanning or rejects explicitly rather than silently waiting under an excluding filter.

### BLE-13 — An iOS notification can be mistaken for a pending read response (P1)

**Files:** [`ios/Owned/OwnedCoreBluetoothProtocolRadio.swift`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/ios/Owned/OwnedCoreBluetoothProtocolRadio.swift)

**Symbols:** `read`, `peripheral(_:didUpdateValueFor:error:)`.

**Trigger:** Read a characteristic while its notifications are active, and a notification arrives before the read response.

**Root cause:** The callback first removes pendingRead[address], completes that read, and returns. CoreBluetooth uses this callback for both read results and unsolicited notifications, so the next callback is not reliable evidence of a read response.

**Impact:** A read can receive an unrelated notification value, that notification disappears from its stream, and the actual read response may subsequently be emitted as a notification.

**Proposed fix:**

1. Make this ambiguity explicit at the adapter contract. The safest default is to reject an independent read while that characteristic is actively notifying, unless a supported unambiguous strategy exists.
2. Alternatively expose honest value-update semantics, or an explicit coordinated stop/read/restore operation with its interruption cost and ownership rules documented.
3. Do not attempt to fix this by assuming callback order or merely serializing local read requests.

**Required regression checks:**

- Use distinct notification and read-response values; deliver the notification before the response.
- Verify neither value is misattributed under the chosen policy.
- Cover read cancellation, repeated reads, and active multi-consumer notification ownership.

**Qualification:** The native Electron/macOS callback implementation was not fully audited in this pass, so this finding is not automatically extended to that implementation.

**Primary platform references:** [Documentation 1](https://developer.apple.com/documentation/corebluetooth/cbperipheraldelegate/peripheral(_:didupdatevaluefor:error:)-1xyna)

### BLE-14 — Android local notification-registration failure is labeled as proven link loss (P2)

**Files:** [`android/src/main/java/com/sfourdrinier/unifiedblemanager/radio/OwnedAndroidGattRadio.kt`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/android/src/main/java/com/sfourdrinier/unifiedblemanager/radio/OwnedAndroidGattRadio.kt)

**Symbols:** `classifyAndroidNotificationRegistrationFailure`.

**Trigger:** setCharacteristicNotification returns false, or local registration rollback is rejected without an authoritative disconnect callback.

**Root cause:** classifyAndroidNotificationRegistrationFailure creates AndroidGattOperationFailure with isLinkLoss=true. Related rollback branches also upgrade failures to link loss. A failed local registration is not by itself proof that the peer terminated the physical link.

**Impact:** Error attribution becomes misleading and can drive inappropriate downstream reconnect behavior or hide a registration/rollback defect.

**Proposed fix:**

1. Represent local notification-registration failure and uncertain physical state separately from confirmed link loss.
2. Use the connection-state callback and generation-matched native evidence to establish physical disconnection.
3. Preserve rollback failure as a cleanup obligation rather than converting it into a stronger, unsupported fact.

**Required regression checks:**

- Return false for local notification registration while a generation-matched connection remains connected and a later read succeeds.
- Verify the error is a registration failure, not a fabricated peer-disconnect cause.
- Separately deliver a genuine disconnect and verify correct classification.

**Qualification:** This finding establishes misclassification in the radio layer; it does not claim every application necessarily reconnects in response.

**Primary platform references:** [Documentation 1](https://developer.android.com/reference/android/bluetooth/BluetoothGatt#setCharacteristicNotification(android.bluetooth.BluetoothGattCharacteristic,%20boolean))

### BLE-15 — WinRT discards notifications arriving during subscription enablement (P1)

**Files:** [`src/backends/winrt/winrt-subscription-runtime.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/winrt/winrt-subscription-runtime.ts); [`src/backends/winrt/winrt-gatt-operations.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/winrt/winrt-gatt-operations.ts)

**Symbols:** `emitWinRtNotification`, `beginPhysicalSubscriptionEnablement`, `enableSubscriptionCompletion`.

**Trigger:** The boundary delivers a notification after registering its listener but before its enable-completion promise settles, or before the logical subscriber has been installed.

**Root cause:** emitWinRtNotification returns unless the physical state is ready. Readiness is set after native completion, and logical consumers are created after awaiting enablement. There is no bounded staging queue for accepted ingress in this interval.

**Impact:** The first sensor packet or a startup response can disappear even though subscribe eventually succeeds.

**Proposed fix:**

1. Install bounded pending-consumer ingress ownership before enabling notifications.
2. Stage early values with item/byte limits and flush them in order only to successfully admitted subscribers.
3. Discard/terminalize the staging buffer on failure or cancellation, with an explicit overflow outcome.

**Required regression checks:**

- Have a fake boundary emit synchronously and asynchronously before its completion promise resolves.
- After successful subscribe, assert the first accepted value is present exactly once and in order.
- Exercise cancellation and overflow during enablement.

**Qualification:** The code proves the drop when the boundary emits in this interval; frequency on particular Windows drivers/sensors requires hardware qualification.

### BLE-16 — WinRT subscription invalidation can block native disconnect behind an unbounded await (P1)

**Files:** [`src/backends/winrt/winrt-subscription-runtime.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/winrt/winrt-subscription-runtime.ts); [`src/backends/winrt/winrt-backend.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/winrt/winrt-backend.ts); [`src/backends/winrt/winrt-gatt-operations.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/winrt/winrt-gatt-operations.ts)

**Symbols:** `invalidateWinRtPhysicalSubscription`, `invalidateConnectionChildren`, `disconnectInternal`.

**Trigger:** A subscription enable is in flight. Cancellation is only acknowledged or stalls, while native enablement does not reach completion.

**Root cause:** Subscription invalidation awaits cancellation and physical.enablement without its own deadline. disconnectInternal awaits invalidateConnectionChildren before attempting native disconnect. Bounded stop-notify helpers do not bound these surrounding waits.

**Impact:** Disconnect can hang behind precisely the native work that physical disconnection may be needed to terminate. Cleanup does not reach its later bounded phases.

**Proposed fix:**

1. Bound each public cleanup phase while retaining unresolved physical work.
2. Do not require indefinite enablement settlement before initiating a generation-safe physical disconnect.
3. Return an honest cleanup-pending/failure record when needed, and reconcile late completion against the retained generation.

**Required regression checks:**

- Keep native notification enable pending indefinitely; let cancellation return cancellation-requested.
- Verify disconnect settles within its cleanup budget and follows the documented physical-disconnect escalation path.
- Resolve the old enable late; assert it cannot create a live subscription in a replacement connection.

### BLE-17 — Pair-cancellation waits can ignore deadline/abort options (P2)

**Files:** [`src/backends/reactnative/react-native-android-security.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/reactnative/react-native-android-security.ts); [`src/backends/winrt/winrt-security.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/backends/winrt/winrt-security.ts)

**Symbols:** `ReactNativeAndroidSecurityBackend.cancelPairing`, `WinRtSecurityBackend.cancelPairing`.

**Trigger:** The native cancellation acknowledgement or the pairing result remains pending beyond the cancellation caller’s deadline.

**Root cause:** Android cancelPairing ignores _options and awaits both native cancellation and the pairing result. WinRT awaits the initial requestCancellation before entering its bounded dispatcher, and also awaits active.result outside the dispatcher completion on relevant paths.

**Impact:** A cancel action can hang or outlive its deadline even while the rest of the API presents deadline-aware operations.

**Proposed fix:**

1. Validate admission before any native side effect and bound the whole cancellation transaction, including acknowledgement and the pairing result.
2. Keep pairing’s actual terminal result authoritative: a timed-out wait must not be reported as successful physical cancellation.
3. Retain the active pairing for eventual reconciliation instead of deleting ownership when the waiting caller gives up.

**Required regression checks:**

- Test pre-aborted calls, never-resolving acknowledgement, and acknowledgement followed by a never-resolving pair result.
- Test a pairing that wins the race and completes successfully; cancellation must report that actual outcome.
- Cover multiple cancel waiters with independent deadlines.

### BLE-18 — Web adapter watch has no source for spontaneous availability changes (P2)

**Files:** [`src/web/web-bluetooth-backend.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/web/web-bluetooth-backend.ts); [`src/web/navigator-web-bluetooth-boundary.ts`](https://github.com/sfourdrinier/unified-ble-manager/blob/a849a54da66ebe475bd7cd57481989fc732dfdd0/src/web/navigator-web-bluetooth-boundary.ts)

**Symbols:** `watchAdapterState`, `currentAdapterState`, `refreshAttachmentAvailability`, `NavigatorWebBluetoothBoundary`.

**Trigger:** A browser-supported adapter availability change occurs after a watch is installed, without another API operation querying current state.

**Root cause:** watchAdapterState samples current state and registers a stream. The navigator boundary does not wire an availability-change event, and there is no ongoing availability poll feeding that watch. refreshAttachmentAvailability only runs when another operation samples availability.

**Impact:** A supposedly live adapter watch can remain stale until an unrelated API call happens.

**Proposed fix:**

1. Add an optional availability-change source to the browser boundary and remove its listener when the last owner is released.
2. Use a bounded shared polling fallback only where necessary and expose its limitations.
3. Do not convert browser availability into a claim about physical power; those are different concepts.

**Required regression checks:**

- Install a watch; change fake browser availability without issuing any other manager request; expect a transition.
- Verify listener/poll cleanup after the last watch closes and after page/backend destruction.
- Test missing browser availability-event support with the documented fallback.

**Qualification:** This concerns availability, not a claim that getAvailability reliably reports the Bluetooth power switch.

**Primary platform references:** [Documentation 1](https://webbluetoothcg.github.io/web-bluetooth/)

## Why these bugs recur

The repeated pattern is divergence between logical state and native ownership. A stream ends before its native resource stops; a caller times out while its native operation continues; a callback is accepted using an identity checked before an await; an unused output queue controls an active consumer; or a shared operating-system state is mistaken for this client’s ownership. The existing ownership/generation design is valuable, but those invariants need to be applied consistently across every terminal path.

## Structural improvements

### Unify ownership transitions, not platform radio semantics

Give every native acquisition an owner before dispatch and a lifecycle through acquiring, adopted, cleanup-pending, and released. Use a shared tested pattern for retaining late results and cleanup failures; keep platform-specific native evidence and pairing/notification semantics explicit. Start with narrow helpers rather than a wholesale rewrite.

### Separate public settlement from physical completion

Track the public result, native completion, and cleanup receipt as distinct objects. Deadlines can terminate a caller’s wait without claiming native work stopped. Disconnect must have a bounded escalation path when child work cannot settle.

### Make generation checks mandatory after every await that mutates ownership

Review callbacks and compensation paths for lease, attachment, connection, database, scan, and subscription generations. A lookup by window/peer ID alone is insufficient after asynchronous suspension.

### Make backpressure local, measurable, and compatible with cleanup

Separate subscriber data budgets, pending event acknowledgements, live-operation quotas, completed replay records, and cleanup/control capacity. Publish counters and terminal causes for each. A stalled view must not silently corrupt an unrelated view.

### Specify data provenance and first-packet guarantees

Define when notification ownership begins, how enablement-time ingress is buffered, and which APIs expose unsolicited notifications versus generic value updates. Audit cached Tauri scan replay separately from fresh radio sightings before relying on lost-device timers.

### Use a lifecycle race matrix and invariant/property tests

For scan, connect, discover, subscribe, and pair: test cancellation before dispatch, during native work, after native success but before adoption, while cleanup is pending, after lease replacement, and after adapter loss. Inject failure on the first cleanup attempt. Assert exact owner counts, no stale-generation delivery, one public terminal, bounded buffers, and eventual release after recoverable faults.

## Suggested implementation order

First address BLE-01 through BLE-03, BLE-10, BLE-13, BLE-15, and BLE-16: they cover wedged ownership, cleanup ordering, and lost/misattributed data. Then close the shared lifecycle/public API cases BLE-04 through BLE-08 and deadline cancellation BLE-17. Finish the remaining BlueZ coexistence/address/deadline and Android/Web contract fixes. Group related fixes into narrowly scoped PRs with failing-before/passing-after regression evidence. Do not disable replay checks, inflate all buffers, swallow cleanup errors, or report cancellation acknowledgement as physical completion.

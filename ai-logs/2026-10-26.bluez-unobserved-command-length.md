# BlueZ unobserved command write length (5.1.3)

- Cause: with `GattCharacteristic1.MTU` withheld, `bluez_write_limits(None)` is
  `(512, 512)`, the finding-97 admission bound that lets BlueZ answer. The same
  value fed `maximumWriteLength`, so the without-response query reported 512, which
  no single ATT command can carry. A consumer (Polar PSFTP framing) sized frames
  from it.
- Rejected: reporting 20. That reinstates the finding-97 defect, because the
  query and admission share one limit, so UBM would refuse commands BlueZ carries.
- Change: `RadioBoundary::observed_write_limit` is separate from
  `write_limits`. It defaults to the admission limit; BlueZ answers
  `capability.unavailable` with the reason for an unobserved command limit. NAPI
  `DispatchRadio` forwards it; `FakeRadio::withhold_observed_write_limit` scripts it.
  Both `gatt.maximum-write-length` routes read it; write admission is unchanged.
- Tests: `f97_bluez_reports_a_command_limit_only_from_a_reported_mtu`,
  `an_unobserved_mode_reports_unavailable_while_writes_stay_admitted`.
- Follow-up (not changed): `bluez_reported_mtu` still folds a D-Bus error into
  "MTU withheld" (`.ok().flatten()`).
